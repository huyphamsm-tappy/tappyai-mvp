## B7-A — resolve photos for the places that are actually used

### The problem, restated with the two numbers that matter

`searchPlaces` resolved photos for **up to 8** places (Google branch) or **up to
10** (OSM branch). The injector enriches **at most 3** for prose. Five to seven
places' worth of resolution was discarded every search.

Each discarded place cost, on the Google branch: 1 og:image fetch + **1 billable
Places Details** + **1 billable Places Photo** + **1 billable Serper Images**.

### What changed

Photos are now fetched at **injection time**, inside
`applyPlaceEnrichmentStreamFilter`, where the finished reply is already known —
so the set of places is exactly the set that will be enriched.

```
before:  tool ──[resolve 8-10 blind]──► model ──► inject (uses ≤3)
after:   tool ──────────────────────► model ──► select ──[resolve those]──► inject
```

`selectPlacesNeedingEnrichment()` mirrors the injector: prose → the mentioned
places, capped at 3; **`[TAPPY_PLAN]` → every place matching a plan item, uncapped**
(6–10 is normal for a trip and must not be truncated).

The resolver is injected by the route, so `streamEnrichment` keeps no tool or
vendor imports and the pre-existing tests still run with no network.

### Measured — local, OSM branch

| Metric | Before | After |
|---|---:|---:|
| Photo-source attempts / search (OSM branch) | **10** | **2** |
| — measured how | Phase A log: 10 `serper_skip` lines, one per result | 6 attempts across 3 searches |
| Places Details calls | *not exercised locally* | *not exercised locally* |
| Model-facing tokens | 753 | **753** (unchanged — B4 already did this) |
| User-facing enrichment | order links only (no photos available) | **order links, now on 3 places instead of 0** |

### The photo/link coupling — fixed

`injectPlaceEnrichment` required a photo before injecting anything, so a failed
photo lookup silently took the order/platform links down with it. Nothing about
an order link needs a photo. The filter is now `hasPhoto(p) || hasLinks(p)`.

**Measured end-to-end with zero photos available** (no Serper key locally):

```
order-link occurrences in PROSE (injected): 9      <- 3 places x 3 links
order-link occurrences in CTA block       : 0
images in prose                           : 0
```

Before B7-A that prose count would have been **0**. Bilingual re-check: order
links now injected on 3 of 4 place queries (was 1 of 4).

### Latency

Resolution moved from *before* generation to *after* it. Total wall-clock is
similar — the reply text is buffered until `d:` either way — and 2–3 parallel
lookups replace 8–10. Not isolated in these measurements; the request timings
above include LLM time.

## B7-B-0 — cache-key normalization

All nine tool cache keys now come from one module, `tools/cacheKeys.ts`, so the
rules are visible together and testable without a network call.

### Fixed

| defect | fix |
|---|---|
| Unicode: `ế` precomposed vs decomposed → two keys for identical text | `.normalize('NFC')` |
| whitespace/case variants fragment keys | collapse runs, trim, lowercase |
| **`weather:` keyed on raw input** — `Hà Nội` / `ha noi` / `HN` were **3 keys for 1 upstream call** | key on the **resolved** city (`resolveWeatherPlace`), which is what wttr.in is actually called with |
| **`gold:` keyed on `query`** — but `getGoldPrice` never reads it (fixed URL, fixed code list), so every phrasing split one answer | **`query` removed from the key** |

### Deliberately NOT fixed: diacritic stripping

My own B7 analysis called this a defect. On inspection it is not one, and doing
it would be a correctness bug:

- the query is handed **verbatim** to Google Places as `textQuery`, so
  `quán ăn` and `quan an` are genuinely different upstream calls;
- stripping tone marks merges distinct Vietnamese words (`mắt` / `mất` / `mát` →
  `mat`), which would serve one query's results for another.

Folding *is* applied in the one place the code already canonicalizes — the
weather city map — where the upstream call is provably identical.

### Safety verified by test

same request → same key · different request → different key · VI and EN never
collide · location, budget, dates, direction and mode all still discriminate ·
GPS precision unchanged (2 dp, ~1.1 km) · no two tools can produce the same key.

## Cross-platform

Backend/tool-layer only. No wire-format change: the same `0:` / `9:` / `a:` /
`d:` frames, same order, same markdown. Enrichment still arrives as markdown
inside `0:` text frames. **No client change made or required** — web reads
`toolName`/`state`, Android reads `0:` only, iOS switches on `0/f/9/a/e/d`.

## Bilingual

VI and EN place queries both return correct replies with enrichment. Cache keys
keep `lang` in every position and were tested for VI/EN collision. The one
`lang=FAIL` in the harness output is a **fixture artifact**, already documented in
B4: an English reply about Vietnamese restaurants necessarily contains Vietnamese
place names, which the detector counts as Vietnamese.

## Remaining risks

1. **The −55 % billable-call figure is an estimate.** Only the OSM branch runs
   locally. First production traffic is the real measurement.
2. **Photo resolution now happens after generation**, so a slow lookup delays the
   final frame rather than the tool call. Bounded by the same per-source timeouts
   (1.8 s / 2.5 s / 4 s) and wrapped so a failure costs photos, never the answer.
3. **Fallback selection when the reply names no place**: the leading 3 are used,
   same as before, so a reply that names nothing still gets plausible enrichment.
4. `get_hotel_prices` and `search_products` still resolve photos eagerly (1 Serper
   Images call per result). Same waste pattern, much smaller; deliberately left
   out of scope.
5. **Google Places Console action still outstanding** — see below.

## Outstanding owner action (unchanged from the B7 analysis)

`food.ts` previously noted that `places.photos` was excluded from the Places Text
Search field mask because *"key is restricted to old Places API only — new API
silently returns 0 photos"*. If that key restriction were lifted, the Text Search
response would carry photo references directly and **every Places Details call
would disappear**, on top of the reduction B7-A already delivers.

That is a Google Cloud Console change on the API key. **Not touched.**
