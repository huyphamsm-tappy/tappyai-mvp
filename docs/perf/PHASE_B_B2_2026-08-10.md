# Phase B — B2: chitchat / no-tool prompt economics

Measured **2026-08-10**, branch `perf/chat-cost-phase-b`, on top of B1.
Local `next dev` :3100, real Anthropic API, anonymous turns.
Pricing: Haiku 4.5 list — $1.00/MTok in, $5.00/MTok out; cache write ×1.25, read ×0.1.

Same limitations as the baseline: `GOOGLE_PLACES_API_KEY`/`SERPER_API_KEY` pull
empty locally, so tool turns run the OSM/DuckDuckGo fallback; latency is dev
latency. Neither affects the chitchat path, which calls no tools at all.

## 1. Options measured

Chitchat declares all 10 tools, then runs with `maxSteps: 1`.

| | measured |
|---|---:|

| cache creation | **0** |

| uncached | 2 628 |

Nothing caches: the chitchat prefix (tools ≈2 290 + simple prompt ≈340 = ~2 630)

**Option A is also incorrect.** `maxSteps: 1` means a tool call has no second

```

f02 "ok show me cafes in Hanoi"    chitchat  tool=[search_places]   chars=0  *** EMPTY REPLY ***
```

2 of 16 probe turns returned an empty reply to the user.

## 2. The key economic question

> **Does removing tool definitions save more than the cache fragmentation it introduces?**

**Yes — because the fragmentation is exactly zero.** The calculation:

```
fragmentation cost = (cache entries destroyed) x (their re-creation cost)

Before B2, chitchat prefix = [tools ~2,290] + [simple prompt ~340] = ~2,630 tok
                           = 2,630 < 4,096  (Haiku 4.5 minimum cacheable prefix)
                           => no cache entry ever existed
                           => measured create=0, read=0 on 12/12 chitchat turns

After  B2, chitchat prefix = [simple prompt ~340]        =   368 tok
                           = 368 < 4,096  => still no cache entry
                           => measured create=0, read=0 on 7/7 chitchat turns

fragmentation cost = 0 entries x anything = 0
saving             = 2,628 - 368          = 2,260 billed units per chitchat turn  (-86.0%)
```

The tool path is untouched. It never shared a cache lineage with chitchat — the
two prefixes diverge immediately after the tool block, and there is no
breakpoint there — so its create/read behaviour is unchanged (hit rate 83.3 % →
87.5 % across the two probe runs, within run-to-run variance).

**Net: −2 260 billed input units per chitchat turn, at no cache cost.**

Fleet impact depends on what share of production traffic is genuine chitchat.
That is **not measurable from here** — it needs production telemetry, which the
B3 `intent` field now records.

## 3. Chitchat scope — what actually qualifies

`classifyIntent` had **no test coverage**, and its pattern was an unanchored
prefix match:

```js
/^(chao|hi|hello|alo|xin chao|cam on|thank|thanks|ok|oke|okie|uh|u|um|tam biet|bye|...)/i
```

`"hiện"` starts with `hi`. `"uống"` starts with `u`. `"ok show me cafes"` starts
with `ok`. All were classified chitchat. Under Option A that produced empty
replies; under Option B it would have produced a capable-but-toolless answer to
a question that needed a tool. **The classifier had to be fixed for B2 to be
safe**, so it is part of B2 rather than a separate change.

The rule is now: *the message must BE a greeting, not merely start with one* —
the pattern must consume the whole message, allowing only polite particles and
punctuation after it.

Measured effect on the 16-case probe:

| case | before | after |
|---|---|---|
| `hiện tại giá vàng bao nhiêu` | chitchat → **empty reply** | tool → 456-char answer |
| `ok show me cafes in Hanoi` | chitchat → **empty reply** | tool → 1 126-char answer |
| `uống gì ngon ở quận 1` | chitchat → generic | tool → 1 388-char answer |
| `ok cho mình xem quán ăn quận 1` | chitchat → 54 chars | tool → 930-char answer |
| `hi-end restaurants in Hanoi` | chitchat → 108 chars | tool → 1 287-char answer |
| genuine chitchat ×7 | chitchat | chitchat *(unchanged)* |

**This makes the run cost more, and it should.** Option A's total for the probe
set was $0.07160 and Option B's was $0.09836 — because five turns stopped
silently dropping the work they were asked to do. The two effects must not be
netted against each other:

- **tool-definition removal** — pure saving, −86.0 % on the chitchat path
- **classifier fix** — a correctness fix that costs money and buys 2 eliminated
  empty replies plus 5 correctly-routed requests

The 40-character ceiling above which everything is `tool` is **unchanged**.
Longer social messages ("cảm ơn bạn nhiều nhé, mình sẽ thử quán đó…") keep the
full path — after B1 that prefix is a cache read, so the cost is small and
widening the chitchat net would add misclassification risk for little gain.

## 4. Bilingual verification

Removing ~2 300 tokens of tool definitions left the (Vietnamese) simple prompt as
~90 % of a very small context, and its language override was itself written in
Vietnamese — unlike `buildSystem`'s, which is in English. A two-word English
turn drifted:

```
"thanks"  Option A -> "You're welcome! 😊 Need help with anything? I can assist with restaurants…"
          Option B -> "Hey! 👋 Welcome to TappyAI. Cần giúp gì không? Mình có thể tư vấn về…"   REGRESSION
```

Fixed by stating the override in the target language and repeating it as the last
line before generation — the same placement `buildPlanningBlock` already relies
on. Re-verified:

| set | result |
|---|---|
| English chitchat ×8 (`hello`, `thanks`, `hi`, `thank you`, `ok`, `bye`, `thanks so much`, `hi there`) | **8/8 English** |
| Vietnamese chitchat ×6 (`chào`, `cảm ơn`, `cảm ơn nhé`, `tạm biệt`, `bạn là ai`, `chào Tappy`) | **6/6 Vietnamese, diacritics intact** |

Detection is by Vietnamese-exclusive letters, not word lists, so an ASCII-only
reply cannot pass by accident.

> `ok` is **not** a valid Vietnamese fixture: it carries no diacritics, and
> `detectLang` documents undiacriticised input as genuinely ambiguous. It is
> covered on the English side instead.

## 5. Cross-platform

Backend-only; **no wire-format change**. B2 only *removes* `9:` (tool call) and
`a:` (tool result) frames from chitchat turns — a strict subset of what already
shipped.

| client | frame handling | impact |
|---|---|---|
| Web | `useChat` (AI SDK) | none |
| Android | `parseTextDelta` reads `0:` only, skips all others | none |
| iOS | `DataStreamLineParser` switches on `0/f/9/a/e/d`, `.unknown` otherwise | none |

No client change was required, and none was made. Chitchat turns now always
produce text, which strictly improves every client (an empty assistant bubble
was previously possible on all three).
