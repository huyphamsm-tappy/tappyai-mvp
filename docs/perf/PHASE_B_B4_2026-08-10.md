# Phase B — B4: slim model-facing tool results

Measured **2026-08-10**, branch `perf/chat-cost-phase-b`, on top of **B1 + B2**.
Local `next dev` :3100, real Anthropic API, anonymous turns.
Pricing: Haiku 4.5 list — $1.00/MTok in, $5.00/MTok out; cache write ×1.25, read ×0.1.

---

## 1. What was wrong

`search_places`, `get_hotel_prices` and `search_products` return two different
kinds of thing in one object:

- **facts the model reasons and writes with** — name, address, ratings,
  `maps_link`, `website_uri`, cuisine, opening hours, prices;
- **enrichment the model is forbidden to write** — `photo_url`, `photo_urls`,
  `order_links`, `platform_links`. The system prompt says so explicitly
  (*"HE THONG TU CHEN, BAN KHONG VIET"*), and `applyPlaceEnrichmentStreamFilter`
  injects them positionally **after** generation, stripping any copy the model
  wrote itself.

The second group was paid context that could not legally be used — and it is the
bulk of the payload: gstatic photo URLs run 180–250 chars each, up to three per
place, plus three percent-encoded order links per place.

**Critically, tool results sit *after* the cache breakpoint**, so unlike the
system prompt they are billed at the full 1.0× rate on every step that carries
them. This is the most expensive kind of token in the request.

---

## 2. Why not the AI SDK's own hook

`experimental_toToolResultContent` looks like the right tool, and is not:
`ai@4.3.19` uses its return value for **both** the model-facing content and the
`result` that reaches the client stream (dist lines 1835-1840 and 1930-1935). It
cannot make the two differ, which is the entire requirement here.

## 3. Design — request-scoped collector

```
tool.execute() ── splitToolResult(name, result) ──┬── model  → returned to the LLM (slim)
                                                  └── enrichment → collector.add()
                                                                      │
route: applyPlaceEnrichmentStreamFilter(response, lang, collector) ────┘
```

`createEnrichmentCollector()` closes over a local array and is created as a
`const` inside the request handler.

| requirement | how it is met |
|---|---|
| request-scoped | a local `const` in the route handler; lives and dies with the request |
| safe under concurrency | each request closes over its own array; nothing shared |
| not global mutable state | no module-level store, no key, no eviction, no TTL |
| no cross-user leakage | there is no lookup path from one request to another's array |
| not instance-dependent | nothing persists between invocations, warm or cold |
| streaming-compatible | tools run before the text they enrich; the filter reads at `d:` |
| compatible with the existing filter | added as an optional 3rd parameter — with none, it reads `a:` frames exactly as before |

**No Redis.** There is nothing to share across instances: the collector is
populated and consumed inside a single request.

Backwards compatible: called without a collector, the filter behaves exactly as
it did, which is what the pre-existing 352-line test suite still exercises.

## 4. Before / after — model-facing payload

Tokenized by the provider itself (`promptTokens` on a `maxTokens:1` call), not
estimated from character counts — gstatic URLs and Vietnamese names tokenize very
differently.

| payload | before | after | reduction | chars |
|---|---:|---:|---:|---|
| **Production-shaped** — 8 places, Google Places branch, 3 photos + 3 order links each, 6 price results | **5 860** | **1 925** | **−67.2 %** | 10 634 → 3 922 |
| **Live `search_places`** — OSM fallback, 10 places | **2 564** | **753** | **−70.6 %** | 5 215 → 1 801 |

- model-relevant tokens retained: **1 925** (prod-shaped) / **753** (live)
- enrichment-only tokens removed from model context: **3 935** / **1 811**
- enrichment retained server-side: **all of it** — 10/10 places on the live call

Because tool results are billed uncached at 1.0×, the production-shaped saving is
**≈3 935 billed input units per place-search step**, and it multiplies on
multi-step turns where earlier results are re-sent.

### End-to-end, 24-turn benchmark

| Metric | baseline | after B1 | **after B1+B2+B4** |
|---|---:|---:|---:|
| **Uncached input** (where tool results live) | 45 750 | 89 290 | **69 939** |
| Cache creation | 179 190 | 25 146 | **0** |
| Cache read | 318 476 | 517 935 | 555 728 |
| Cache hit rate | 64.0 % | 95.4 % | **100 %** |
| **Billed input units** | 301 585 | 172 516 | **125 512** |
| Output tokens | 9 312 | 13 247 | 12 447 |
| LLM calls | 42 | 46 | 46 |
| Tool calls | 26 | 32 | 32 |
| **Estimated cost** | $0.34815 | $0.23875 | **$0.18775** |
| Mean latency (dev) | 12 821 ms | 16 877 ms | 15 339 ms |
| Mean TTFB (dev) | 1 508 ms | 4 865 ms | 3 688 ms |

Uncached tokens **per tool turn**: 3 872 (after B1) → 3 143 (after B1+B2+B4),
**−18.8 %**. That end-to-end figure is confounded by B2 landing in between and by
run-to-run tool-count variance; the **−67.2 % payload measurement is the clean
B4 number**.

Latency did not regress — slightly better, within noise.

## 5. Production-path limitation (unchanged, still applies)

`GOOGLE_PLACES_API_KEY` and `SERPER_API_KEY` pull as empty strings from Vercel
(Sensitive variables), so locally:

- `search_places` runs the **OSM/Overpass fallback**;
- `fetchPlacePhotosByName` returns nothing, so **there are no photos at all**.

`injectPlaceEnrichment` only injects for places that *have* a photo
(`usable = places.filter(p => p.name && (photo_urls?.length || photo_url))`), so
**end-to-end photo and link injection cannot be observed on this machine**. That
is a pre-existing property of the injector, not a B4 change.

What that means for the evidence:

| claim | how it is evidenced |
|---|---|
| enrichment no longer reaches the model | **measured** — live wire capture, `a:` frame keys are `address, amenity_type, count, cuisine, google_maps_search, location, maps_link, name, note, phone, result, results, source, wifi`; no `photo_url`, `photo_urls`, `order_links`, `platform_links` |
| payload reduction | **measured** with the provider tokenizer (live + production-shaped fixture) |
| enrichment still reaches the user | **unit-tested** against the exact collector→filter path (photos, order links, platform links, plan photos, multi-search accumulation) — *not* observable end-to-end locally |
| production payload shape | **modelled**, clearly labelled; the live OSM figure is a **floor**, since the Google Places branch carries more enrichment per place |

Vercel Deployment Protection was **not** modified, and no owner-only setting was
touched or requested.

## 6. Tests

Written **before** the implementation; both files failed to load (the module did
not exist), then the invariants were driven green.

**New — `toolResultSplit.test.ts` (11 cases)**
strips every enrichment key · keeps every model-relevant field · returns
enrichment for injection · handles `search_results`-shaped tools (hotels,
products) with `title`→`name` · leaves non-place tools untouched · survives
`null`/`{}`/`42`/`'text'`/malformed without throwing · collector: request
isolation, multi-call accumulation, dedupe-and-upgrade, ignores nameless entries.

**New — `streamEnrichment.test.ts` (6 cases)**
photo injected from collector only · order links from collector only · platform
links from collector only · multi-search trip plan · **one request's collector
never enriches another's stream** · still works with no collector (legacy path).

**Mutations — 3 applied, 3 RED**

| mutation | caught by |
|---|---|
| model result not slimmed (`return item`) | `"photo_url" must not reach the model` |
| filter ignores the collector | `expected … to contain 'ga.jpg'` (+4 more) |
| collector backed by a module-level array | `expected [ 'A place', 'B place' ] to deeply equal [ 'A place' ]` |

**Suite**: 1 079 passed / 0 failed (excluding the four pre-existing sources).
**Architecture guard**: 8/8.

## 7. Cross-platform

Backend-only. The `a:` frames still exist and still carry the tool result — they
are simply smaller. No frame type added or removed, no field renamed.

Verified that **no client reads the enrichment fields**:

| client | what it does with tool frames |
|---|---|
| Web | reads `toolInvocations[].toolName` / `.state` only, for the "đang tìm…" hint |
| Android | `parseTextDelta` handles `0:` and skips every other prefix |
| iOS | `DataStreamLineParser` decodes `9:`/`a:` and stores the payload opaquely to mark `.result(...)`; never parses enrichment out of it |

All user-visible enrichment arrives as markdown inside `0:` text frames, which is
unchanged. **No client change was made or required.**

## 8. Bilingual

| check | result |
|---|---|
| VI place queries (`Gợi ý quán ăn ngon ở Quận 1`, `Quán cà phê đẹp ở Hà Nội`, `Tìm nhà hàng hải sản ở Đà Nẵng`) ×2 rounds | **6/6 Vietnamese** |
| EN place queries (`Suggest good restaurants in District 1`, `Find good cafes in Da Nang`) | English, place names intact |
| CTA blocks | present on all four place turns |

**One English reply to a Vietnamese query was observed once**, on the wire
capture immediately after the change. Six subsequent runs of the same three
queries returned Vietnamese, and all eight pre-B4 runs of the same queries were
Vietnamese — **1/9 after, 0/8 before**.

Not enough to establish a regression, and the B2 mechanism does not transfer:
B2 removed ~2 300 tokens of Vietnamese *prose*, whereas B4 removes only
percent-encoded and gstatic **ASCII URLs** while retaining every Vietnamese
field (`name`, `address`, `cuisine`, `note`). Recorded as a risk to watch in
production rather than dismissed.

## 9. Remaining risks

1. **Production enrichment injection is unverified end-to-end.** Unit tests cover
   the collector→filter path exactly, but no local run can exercise it with real
   photos. First production traffic after deploy is the real check.
2. **Language drift, 1/9 observed.** See §8. Cheap mitigation if it recurs: a
   Vietnamese-side reinforcement in the dynamic segment, mirroring the B2 fix.
   Deliberately **not** done here — outside B4's mandate.
3. **`injectPlaceEnrichment` requires a photo to inject anything**, so with the
   Serper key absent no order/platform links are injected either. Pre-existing,
   unchanged by B4, but worth knowing: if photo lookup fails in production, order
   links silently vanish too.
4. Non-place tools are untouched; `web_search`, `get_news`, `get_weather` etc.
   keep their full payloads. Not in B4's scope.
