### Upstream economics, read from the code and confirmed against live runs

`searchProducts()` is **not** one upstream call:

* **3** `serperSearch()` calls per invocation, fired in parallel — price, marketplace-site, shop-info.
* plus **one image lookup per returned result**, capped at 8 → `fetchPlacePhotosByName` ×8.
* ⇒ **up to 11 Serper credits per `search_products` call.**

And the model calls it **twice** on a two-way comparison — once per entity. Measured across
the A/B runs: of 19 runs that called it, **19 called it exactly twice** (`{2: 19}`, no other
count observed).

> **⇒ up to 22 Serper credits per product-comparison turn**, against a 2,500/month free tier.
> A 40-request benchmark would spend a material fraction of the monthly quota. This is the
> dominant cost of the whole capability, and §9 shows prefetch does **not** reduce it.

### Option metric — replaced, and its limit stated

`boldSpans` is gone from the option role (kept only as a raw diagnostic). The new metric counts
bold spans that **head a line or list item**, excluding section labels (ending `:` or `?`).

Validated against **18 live replies** captured in §5–§6:

| Reply kind | new metric | old `boldSpans` |
|---|---|---|
| real food comparison | `["Phở","Bún bò"]` → **2** ✅ | 3–4 |
| real hotel comparison | `["My Khe Beach","Da Nang City Centre"]` → **2** ✅ | 4–5 |
| real product comparison | `["iPhone","Samsung"]` → **2** ✅ | 7 |
| pure questionnaire | **0** ✅ | 1–2 ✗ |

**Known false positive — reported, not hidden.** When a clarification question is followed by a
bolded bullet list of *criteria* (`- **Giá rẻ** → …`, `- **Camera chất lượng** → …`), those
criteria are counted as options: `14-vi` scored 5 where the true option count is 0. The metric
is therefore recorded **with `optionsNamed`**, so every count is auditable rather than trusted.
Per the brief, this is stated as a measurement limitation rather than papered over with a more
fragile rule.

## 3. detectLang — impact, fixture, and no silent patch

**`detectLang` was NOT modified.** It remains a C5 concern.

**Impact.** `detectLang('Nên mua iPhone hay Samsung?') === 'en'`, so the owner-approved
scenario is served a prompt whose first block is `CRITICAL LANGUAGE OVERRIDE … MUST be in
English`. Worse than a single sentence: of **seven** natural Vietnamese phrasings of the same
question, only **two** read as `vi`. Even `Tôi nên mua iPhone hay Samsung?` reads as English —
`Tôi` is sentence-initial, so it is not a *lowercase* accented word.

**Fixture strategy.** The route resolves language as
`detectExplicitLangRequest(text) ?? detectLang(text)` and the request body carries no language
field — so there is **no way to inject a language without changing production**. Two fixtures
exist instead, both verified:

| | fixture | resolvedLang | stage | locationIntent | contamination |
|---|---|---|---|---|---|
| **F1** ✅ used | `Nên mua iPhone hay Samsung? Trả lời bằng tiếng Việt.` | **vi** (via the shipped explicit-request path) | comparison | unknown | adds an instruction to the stimulus |
| F2 | `Mình muốn mua điện thoại, nên chọn iPhone hay Samsung?` | vi | comparison | unknown | different sentence |
| — | *original* | **en** ❌ | comparison | unknown | the contamination itself |

**F1 was used** because it exercises a real production feature rather than dodging the
detector, and because it holds `stage` and `locationIntent` constant. The original phrasing was
run **alongside** it in every cell, so the contamination is measured rather than avoided.

## 4. locationIntent — root cause, minimal fix, regression

**Root cause, isolated to one alternative.** Of the 22 sub-patterns in `offlineRe`, exactly one
fires on the failing shopping queries, and it fires **alone**: `\bo\s+dau\b` ("ở đâu"). On
genuine physical-store queries it only ever fires *alongside* a real place marker
(`Đến mua ở đâu tại Quận 3` → `quan N` + `den mua` + `o dau`). English has no equivalent
marker at all, which is exactly why `12-en` called `search_products` and `12-vi` called nothing.

**Minimal correction** ([intent.ts](../../src/lib/ai/intent.ts)) — `ở đâu` / `chỗ nào` moved
out of the hard set into a weak one, consulted **last**, and only when the turn is not a
purchase:

```
if (offlineRe.test(t)) return 'offline'     // real place markers — unchanged, still decisive
if (onlineRe.test(t))  return 'online'      // unchanged
if (weakWhereRe.test(t) && !purchaseRe.test(t)) return 'offline'   // new
return 'unknown'
```

Offline detection was **not** broadened away: every place marker still decides on its own, and
a bare "where" still means offline for everything that is not a purchase.

**Known gap, not fixed (out of scope):** `offlineRe` has no English physical-store vocabulary —
`Physical store near me` returns `unknown`. Pre-existing, unrelated to this defect.

## 5. Scope A/B — Hypothesis A **CONFIRMED** (n = 4 per cell)

Variant **A** = C3-B as it stands. Variant **B** = the same file with **only** the string
`tu van cong nghe chung hoac giai thich cong nghe hoat dong the nao ngoai muc dich mua sam, `
removed. Nothing else changed; the file was restored and hash-verified identical afterwards.

| cell | refused | called `search_products` | clarifications |
|---|---|---|---|
| **A** `Nên mua iPhone hay Samsung?` | **2/4** | 1/4 | 1,2,5,1 |
| **B** same request | **0/4** | **4/4** | 0,1,2,1 |
| **A** F1 fixture (`…Trả lời bằng tiếng Việt`) | **0/4** | **4/4** | 2,2,2,2 |
| **B** F1 fixture | 0/4 | 4/4 | 2,2,2,3 |
| **A** `Should I buy an iPhone or a Samsung?` | 0/4 | 0/4 | 8,8,8,8 |
| **B** same | 0/4 | 0/4 | 8,8,8,8 |

**Three findings.**

1. **The prohibition C3-B added causes the refusal.** With it: 2/4 refusals and only 1/4 turns
   fetched data. Without it: **0/4 refusals and 4/4 fetched data.**
2. **It is an INTERACTION, not a single cause.** The F1 language fixture removes the refusal
   *without touching the prompt at all* (A-fixture: 0/4). The refusal needs **both** the new
   prohibition **and** the English-language contamination from §3. Removing either one is
   sufficient. C3-B.1 proposed these as two separate problems; they are one.
3. **The refusal is stochastic, not categorical.** 2/4 under identical conditions. The C3-B
   report called it categorical on the strength of two runs — that inference does not hold, and
   the same caution applies to every "reproduces in both runs" claim in that document.

**English is untouched by scope:** 0/8 refusals, `clar = 8` in all eight runs, output 133–136
tokens every time. Its behaviour has a different cause — §6.

## 7. Entity extraction — feasible for products, unsafe as a trigger

Measured with the simplest honest splitter (strip decision frame → strip trailing adjunct →
split on `hay / hoặc / với / và / or / vs / and`). **No parser was built for production.**

| slice | EXACT | note |
|---|---|---|
| all 22 probes | **16/22** | 3 PARTIAL, 3 WRONG |
| product-kind only | **13/15** | the required VI and EN forms are 7/7 |
| VI required forms | 4/4 | incl. `So sánh X với Y`, `X vs Y`, brand+model |
| EN required forms | 3/3 | incl. `Which should I buy, X or Y?`, `Compare X and Y` |
| three-way | 1/2 | `X hay Y hay Z` ✅ · `X, Y or Z` ✗ (comma unhandled) |
| separator inside a name | 0/1 | `Black and Decker hay Bosch` → `["Black","Decker","Bosch"]` |

**The failure that matters is not precision — it is the trigger.** `detectDecisionStage`
returns `comparison` for **every** trap:

| request | stage | extracted | should go to `search_products`? |
|---|---|---|---|
| `Quán này hay không?` ("is it any good?") | **comparison** | `["Quan nay","khong"]` | **no — nonsense** |
| `Có quán nào hay ho gần đây không?` | **comparison** | `["Co quan nao","ho gan day khong"]` | **no — nonsense** |
| `Mua iPhone ở Shopee hay Tiki rẻ hơn?` | comparison | `["Mua iPhone o Shopee","Tiki re hon"]` | **no — the entities are STORES** |
| `Nên ở gần biển Mỹ Khê hay…?` | comparison | `["gan bien My Khe", …]` | **no — places** |
| `Nên chọn quán phở hay quán bún bò…?` | comparison | `["quan pho","quan bun bo"]` | **no — dishes** |

**7 of 22 inputs yield two "entities" that must never reach `search_products`, and the
`comparison` gate filters none of them.** Any prefetch keyed on `decisionStage === 'comparison'`
would fire on all seven — burning up to 22 Serper credits on `["Quan nay","khong"]`. A
prefetch bridge needs a second, product-specific gate that does not exist today.

## 8. Architecture comparison

| | Candidate A — server prefetch | **Candidate B — existing tool loop** | Candidate C — SDK upgrade |
|---|---|---|---|
| Works today? | needs building | **yes — measured, 19/19** | no |
| LLM calls | 1 | 2 | 1–2 |
| Forcing | none | none (`toolChoice` stays `auto`) | `prepareStep` |
| Entity extraction | **required** (§7 — unsafe trigger) | **not required** — the model picks the queries | not required |
| Serper credits | same (§9) | same | same |
| B1 cache | data would land in `dynamic` → prefix intact | **untouched** | untouched |
| Risk | fires on the 7 traps; new code on the hot path | **none — no new code** | `ai@5` changes streaming, tool and error semantics; the C2 note warns an upgrade silently switches forcing on |
| New failure modes | extraction bugs, wasted quota | none | migration-wide |

**Candidate B is not a hypothesis — it is an observation.** Across §5–§6, once the scope
prohibition is removed *or* the language is correct, the model chose `search_products` on
**19 of 19** product-comparison runs, twice each, unprompted, at `toolChoice: 'auto'`. The
C3-B claim "comparison never calls `search_products`" was an artefact of the refusal path:
refuse → no tool. **The missing edge in the data flow is real** (C3-B.1 §4 stands, at the code
level) **— it simply turns out not to be needed.**

**Candidate C — documented, not implemented.** `experimental_prepareStep` exists in `ai@4.3.19`
at `dist/index.mjs:4177` inside `generateText` **only**; `streamText` reads `toolChoice` at
`:5196` and re-applies the same outer value inside `streamStep` at `:5654-5656`, every step,
with no per-step override. AI SDK 5 does support `prepareStep` on `streamText` — which is the
migration risk, not the benefit: the deleted C2 code carried an `@ts-ignore` asserting the
option worked, so an upgrade would silently switch forcing on and change both cost and
clarification behaviour. Cost: unchanged upstream; risk: repo-wide.

## 9. Cost comparison — measured, 60 live runs

| path | n | LLM steps | tool calls | `promptTokens` | output tokens | latency |
|---|---|---|---|---|---|---|
| no-tool (single step) | 35 | 1 | 0 | 1,178 | 168 | 3.1 s |
| **tool loop** | 25 | 2 | 2 | 3,307 | 511 | 8.5 s |

⚠️ `promptTokens` **excludes cached tokens** — true input is
`promptTokens + cacheCreation + cacheRead`, and the data stream does not expose the cache
counters to an HTTP client. These are step-sum figures, not full input sizes.

**Upstream is what dominates, and prefetch does not help it:**

| | LLM steps | `searchProducts()` invocations | Serper credits |
|---|---|---|---|
| tool loop (measured) | 2 | 2 | **up to 22** |
| prefetch (estimated) | **1** | 2 | **up to 22** |

> Prefetch's entire saving is **one generation step** — roughly 1,100–2,100 `promptTokens` at
> the cached rate plus one round trip. It buys **nothing** upstream, because the expensive part
> is `searchProducts` itself and both designs call it twice. It would also add the §7 trap
> exposure. **Prefetch is not cheaper in the way C3-B.1 §10-A suggested; that estimate is
> withdrawn.**

## 10. Recommended C3-B.3 architecture

> ### Candidate B — keep the existing tool loop. Build no bridge.
>
> Remove the scope prohibition that blocks product comparison, and treat the language
> contamination as the C5 defect it is. The model then fetches `search_products` on its own,
> at `toolChoice: 'auto'`, with no new code, no forcing, no extra LLM call, no entity
> extractor, and no change to `AI.stream()` or the B1 cache contract.

**Why this and not prefetch.** Prefetch was the C3-B.1 lean. Three measurements moved it:
the tool loop already works (19/19); prefetch saves one generation step and zero upstream
credits (§9); and its trigger cannot be built safely today, because `comparison` fires on
`Quán này hay không?` and the extractor happily returns two entities for it (§7).

**Scope of the proposed C3-B.3, for approval — not started:**

1. Remove only the added prohibition from `scopeBlock`; re-verify with the §5 A/B design at n≥4.
2. Re-run the corrected benchmark **once a Serper key exists** (§1) — before that, grounding
   remains unmeasurable and no grounding claim may be made.
3. Leave `detectLang` to C5. Record the F1 fixture result beside the untreated one so the
   contamination stays visible instead of being designed around.
4. Re-examine the `2–4` contract only with the §2 metric **and** its named list.

**Explicitly not recommended:** any bridge, `forcedTool`, prefetch, `prepareStep`, an SDK
upgrade, a second LLM call, or an entity extractor.
