# C3-B.6 — Missing-evidence structural diagnosis

**Date:** 2026-08-11 · **Branch:** `perf/chat-cost-phase-b` · **HEAD `59ff89a`** · nothing committed, nothing pushed
**No production code changed.** C3-B.5's uncommitted prompt change is preserved exactly
(`promptBuilder.ts` 20/5). Both temporary experiment patches were hash-verified restored.

# VERDICT: OUTCOME C — BLOCKED

The structural direction does not work, for **two independent reasons**, each proven:

1. **The signal cannot be computed.** The premise "the search results do not contain a usable
   price" is false for S3. They *do* contain prices — for **accessories**, in listings whose
   titles name the target product. Nothing in the payload separates them.
2. **The signal does not work even when handed to the model for free.** An explicit,
   unconditional `price_evidence: NOT_VERIFIED … KHÔNG được dẫn giá sản phẩm từ kết quả này`
   made fabrication **worse** (6 → 9 across 3 runs) and never once produced a "not found"
   statement.

---

## 1. Exact tool payload flow

```
Serper /search  (organic[] — title, link, snippet ONLY; no price field, no shopping endpoint)
  → searchProducts()            3 parallel queries; direct-product-link filter; dedup; slice(0,8)
  → photo attach                per result (Serper /images)
  → { query, source, search_results[], shop_info_results[], links[], note }   ── or ──
    { note, links, shop_info_results }                        when search_results is empty
  → forModel() → splitToolResult()   strips photo_url/photo_urls/order_links/platform_links
  → model sees:  search_results[] = { title, link, snippet }
```

**There is no price extraction anywhere in this path.** `grep price|gia|₫|VND` over
`shopping.ts` returns exactly two hits: the literal `' gia Shopee Tiki Lazada'` appended to a
search query, and the `priceDisclaimer` note. `splitToolResult` removes enrichment keys and
passes `...rest` through untouched.

Answers to the seven questions:

| # | question | answer |
|---|---|---|
| 1 | when a result has an explicit price | **never** — no price field exists |
| 2 | when a result has no price | indistinguishable — identical shape |
| 3 | price only inside an unstructured snippet | **the only way a price ever appears** |
| 4 | when extraction fails | there is no extraction to fail |
| 5 | when all candidates lack a price | no signal emitted |
| 6 | does the tool distinguish these | **no** |
| 7 | missing-price signal in the schema | **none** |

## 2. Why S3's missing price is not explicit — and why the premise was wrong

Reproduced `searchProducts()` exactly, without the LLM, for 6 Serper credits.

**`Sony WH-1000XM5` — 14 candidates, 6 carry a price figure:**

| price(s) found | what the listing actually is |
|---|---|
| `15.000₫` | replacement cable |
| `230.177₫`, `701.620₫` | replacement hinge |
| `47.600₫`, `8.761.500₫` | mixed — accessory *and* a plausible product price |
| `7.790.000₫`, `9.490.000₫` | **genuine product price range** ✅ |
| `165.670₫`, `337.810₫` | ear pads |

**`Bose QuietComfort Ultra` — 14 candidates, 4 carry a price figure, and all four are `15.000₫`** —
ear pads, a travel case, a cover. **There is no Bose headphone price in the payload at all.**

> **The decisive detail: `namesTarget` is `yes` for 13 of 14 candidates in both sets.** Accessory
> listings name the product they are *for* — "Đệm tai nghe **Sony WH-1000XM5**", "Ốp Lưng Cho
> **Bose QuietComfort Ultra** Earbuds". So "does this candidate name the product?" cannot
> separate a ₫15,000 ear pad from a ₫8,761,500 headphone.

Against this, C3-B.5's S3 reply claimed Sony `~6.5–7.8M` (evidence says 7.79–9.49M) and Bose
`~8.6–9M` (evidence contains **no** Bose product price). Both attributed to Lazada/Shopee.

**So the model does not receive enough information to know price evidence is absent — but the
deeper problem is that the evidence is not absent, it is *contaminated*.** A `price_status`
field would have to answer "is this price the product's or an accessory's?", and the payload
carries nothing that decides it. A magnitude heuristic would be a guess about the product's
price range, which is exactly the prior knowledge the contract forbids.

## 3. Smallest viable structural signal — and why none qualifies

| candidate signal | computable from this payload? | verdict |
|---|---|---|
| `price_evidence: none` when **no** candidate has any price figure | ✅ trivially | **doesn't apply to S3** — S3 has 4–6 price figures |
| `price_status: found / not_found` per product | ❌ requires accessory-vs-product classification | not computable |
| `price_status: uncertain` when prices vary wildly | ⚠️ heuristic (₫15,000 vs ₫8,761,500) | a guess; would mark the *correct* Sony range uncertain too |
| free-text caveat "figures may be accessory prices" | ✅ constant string | **tested — see §4** |

## 4. A/B result — the signal is not effective

Temporary unconditional patch to `shopping.ts`, 3 runs per variant on the S3 request:

| | money claims not in evidence | says "not found" | pick | avg `promptTokens` |
|---|---|---|---|---|
| **A** current payload | **6** | 0/3 | 1/3 | 9,081 |
| **B** + explicit `price_evidence: NOT_VERIFIED …` | **9** | **0/3** | 0/3 | 9,163 |

The signal was as strong as it can be made: unconditional, explicit, imperative, in Vietnamese
matching the prompt's register, stating outright that no verified price exists and that product
prices must not be quoted from the result. **It changed nothing in the right direction and the
count went up.** `shopping.ts` restored, hash-identical.

This mirrors C3-B.5's finding one layer down: the model reliably uses evidence that *is* present
and reliably ignores instructions about evidence that is *absent* — whether that instruction sits
in the prompt or in the tool payload.

## 5. Client impact (moot, but established)

* The model-facing result **is** emitted to clients — `toDataStreamResponse()` writes it as `a:`
  frames; my probes read them directly.
* **No client source consumes it.** `search_results` / `price_evidence` appear in **zero**
  Kotlin/Java/Swift/TSX source files. The only Android hits are build artifacts
  (`classes.dex`, `mapping/`), not source.
* The one real consumer is server-side: `streamEnrichment.ts` reads `a:` frames and
  `search_results` to inject photos — it selects by name and would ignore an added scalar field.

⇒ A new field would be **model-only in effect**, requiring no Web, Android or iOS change and no
VI/EN work. Wire bytes would grow. This is recorded for completeness; it does not rescue the
approach.

## 6. Token overhead

Measured, not estimated: **+82 `promptTokens` per comparison turn** (9,081 → 9,163) for a
one-line signal on two `search_products` calls. The tool result sits **after** the B1 cache
breakpoint, so this is billed at the full input rate on every such turn — and in this experiment
it bought a *worse* outcome.

## 7. Safety contract — unchanged, and not to be traded away

The invariants stand as written: `found` → usable; `not_found` → never invent, estimate,
interpolate or attribute to a marketplace; `uncertain` → never presented as verified; no
"based on the search results" for unsupported claims; and the payload never proves camera
quality, durability, ecosystem, reliability, resale value or "better overall". **Nothing in this
diagnosis justifies loosening the C3-B.5 qualitative grounding contract** — that contract is
what currently keeps S1 honest.

## 8. Proposed tests — designed, deliberately NOT implemented

Written out so the design is reviewable, but no test file was added, because OUTCOME C means
there is nothing to test yet:

1–3. `price_status` = found / not_found / uncertain each produce the documented model-facing shape
4. mixed candidates (some priced, some not) resolve to a single documented status
5. one product priced, one not → statuses independent per query
6. all candidates unpriced → `not_found`, never an omitted field
7–8. VI and EN requests produce the same status for the same evidence
9. product/model names survive the transform unchanged
10. marketplace attribution survives unchanged
11. `title` / `link` / `snippet` byte-identical to today for every existing case
12. no fabricated price in the reply once the signal is present

**Mutation strategy:** delete the status field; invert `not_found`→`found`; omit the field
instead of emitting `not_found` (the "missing field ≠ licence to estimate" invariant); strip the
per-query independence. Each must turn its test RED — and test 12 is behavioural, which §4 shows
would **not** pass, which is precisely why implementation is not proposed.

## 9. Should C3-B.6 implement?

**No.** Implementing would add per-turn input cost and wire payload for a signal that is
(a) not computable from this retrieval and (b) empirically ineffective.

What would actually be required is a **retrieval change**, which this phase explicitly excludes:
a source that returns *structured* product records with a price field bound to a specific product
— e.g. Serper's shopping endpoint rather than `organic` — so that "no price for this product" is
a fact the tool can state instead of infer. That is a larger redesign and needs its own owner
decision.

## 10. Verdict

# C3-B.6 — OUTCOME C — BLOCKED

**Proven:** no price extraction exists · the payload's prices are predominantly accessory prices
in listings that name the target product · an explicit absence signal is both uncomputable here
and behaviourally ineffective (6 → 9) · adding it costs +82 input tokens/turn · no client change
would be needed if it were ever adopted.

**Not done, per the decision gate:** no production code changed, no tests added, no commit, no
push, no retrieval redesign started.

**Preserved:** C3-B.5's prompt contract remains uncommitted and intact — it is still the only
thing keeping the S1-class comparison grounded, and it should not be reverted on the strength of
this result.

**Owner decision needed:** accept S1-class grounding with S3-class still estimating and monitor,
or authorise a retrieval redesign (structured product/price source) as a separate phase.
