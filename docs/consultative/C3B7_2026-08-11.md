# VERDICT: OUTCOME C — RETRIEVAL REDESIGN REQUIRED (but the missing piece is internal, not external)

Serper `/shopping` **exists, works on this account, is 6× cheaper than the current path, and
solves the evidence-quality problem outright.** It does not, on its own, meet the acceptance bar:
product **identity** cannot yet be determined safely from the model's free-text query, and — the
decisive finding — **the model still states a price when there is no price evidence at all.**

---

## 1–2. Available retrieval options — verified by calling them, not assumed

| endpoint | HTTP | credits | array | fields returned |
|---|---|---|---|---|
| `/search` *(current path)* | 200 | 1 | `organic` | `title, link, snippet, rating, ratingCount, position` |
| **`/shopping`** | **200** | **2** | `shopping` (**40** records) | **`title, source, link, price, imageUrl, productId, position`** |
| `/images` *(current path)* | 200 | 1 | `images` | `title, imageUrl, …` |
| `/places` | 200 | 1 | `places` | `title, address, latitude, longitude, phoneNumber, website, cid` |
| `/news` | 200 | 1 | `news` | `title, link, snippet, date, source, imageUrl` |

`/shopping` is the only mode where **price is a structured field bound to a single product record**,
with an explicit merchant (`source`) and URL. No image lookup is needed — `imageUrl` is included.
It requires no new API capability and coexists with the current tier.

## 3. The two failure classes, replayed

| | current `/search` (organic) | `/shopping` |
|---|---|---|
| **Sony WH-1000XM5** | 6/14 candidates carry a figure — cable ₫15,000, hinge ₫230,177, ear pads ₫165,670; one genuine range | **40/40 records priced, 0 accessories.** ₫3.5M–₫8.09M, merchants: Sony Store, CellphoneS, FPT Shop, Thế Giới Di Động |
| **Bose QuietComfort Ultra** | 4/14 carry a figure — **all four are ₫15,000 accessories. No product price exists at all** | **32/40 verified product records**, ₫4.99M–₫11.99M, merchants named |
| **iPhone 15** | prices buried in snippets | 40/40 priced, ₫10M–₫27.9M |

**The accessory-contamination problem that defeated C3-B.6 does not occur on `/shopping`.** Google
Shopping's index already resolves a product query to product offers; an explicit accessory query
(`đệm tai Sony WH-1000XM5`) returns accessories, and a product query returns products.

⇒ **Price attribution is solved at the record level.** A price now belongs to a titled product
record from a named merchant, not to an arbitrary snippet.

## 4. Product identity — NOT solved, and this is what blocks OUTCOME A

The deterministic rule tested: every significant token of the requested term must appear in the
product title, and the title must not match an accessory lexicon. **No price thresholds** were
used — a magnitude rule would just move the guess server-side, which the brief forbids.

| case | result |
|---|---|
| exact model, EN (`Sony WH-1000XM5`) | ✅ 40 PRODUCT / 0 ACCESSORY |
| exact model (`Bose QuietComfort Ultra`) | ✅ 32 PRODUCT / 1 ACCESSORY / 7 UNRELATED |
| accessory-heavy VI (`đệm tai Sony WH-1000XM5`) | ✅ 18 ACCESSORY correctly flagged |
| **variant (`Samsung Galaxy S24`)** | ❌ **conflates variants** — the PRODUCT set spans S24, S24+, S24 FE and S24 Ultra, giving a range of ₫7.5M–₫31M for "Galaxy S24". `Samsung S24+` and `Galaxy S24 FE` were also *wrongly rejected* as UNRELATED because they omit one required token |
| **brand-only (`iPhone`)** | ❌ 40 PRODUCT spanning iPhone 13 → 17 Pro Max, ₫3.5M–₫61.5M. No single price is meaningful |
| **the model's actual query text** | ❌ **the blocker in practice** — the model sends `"iPhone 15 price Vietnam"`, so the token rule requires `price` and `vietnam` to appear in a Vietnamese product title and matches nothing |

That last row is why the live probe returned `verifiedRecords = 0` on 5 of 6 runs. It is not a
probe bug alone: **the identity rule cannot be applied to the raw model-authored query.** It would
need a query→product-term normalizer plus variant handling — both new heuristic layers that must
themselves be designed and proven.

## 5. Credit economics — structured retrieval is dramatically cheaper

| | per product | per 2-product comparison |
|---|---|---|
| **current** — 3 × `/search` + ~1 `/images` per returned candidate (measured: 3 + 7 + 2 B7-A) | **~12** | **~24** |
| **`/shopping`** — 1 call, `imageUrl` included | **2** | **4** |

**~6× cheaper**, with strictly better evidence. Cost is not an obstacle; it is an argument in
favour.

## 6. Fallback states — representable, and that is not the problem

`FOUND` / `FOUND_NO_PRICE` / `NOT_FOUND` / `AMBIGUOUS` can all be derived deterministically from
`/shopping` **once identity is settled**: a record with a `price` and a confident identity match is
`FOUND`; identity matched with no priced record is `FOUND_NO_PRICE`; no match is `NOT_FOUND`;
multiple incompatible variants (the S24 case) or a brand-only query is `AMBIGUOUS`.

**But representing the state is not the same as the model honouring it — see §10.**

## 7. C3-B.5 contract — preserved, and still load-bearing

Nothing here justifies loosening it. Better evidence does not make the qualitative rule
redundant: `/shopping` proves price, merchant and product identity, and proves **nothing** about
camera quality, durability, ecosystem, reliability or resale value. Those claims remain governed
by C3-B.5, which is exactly what keeps the S1-class answer honest.

## 8. Client impact — model-only, provable

Unchanged from C3-B.6: `search_results` appears in **zero** Kotlin/Java/Swift/TSX source files
(the only Android hits are `classes.dex` build artifacts). The single real consumer is server-side
`streamEnrichment.ts`, which matches on `title` and would be unaffected by added `price`/`source`
fields. ⇒ **Web, Android and iOS need no change; VI/EN parity is unaffected.**

## 9. Token / cache impact

Structured records are *more compact* than today's payload: `{title, price, source}` replaces
`{title, snippet}` where snippets run 100–200 characters. Measured in the probe: `promptTokens`
**3,287–3,367** on runs with no records and **5,132** with 12 records, against **9,081** for the
current organic path on the same request — roughly **40% fewer input tokens** on a comparison
turn. All of it lands in the tool result, i.e. **after** the B1 cache breakpoint; `shared` is
untouched. No verbose metadata is proposed — C3-B.6's mistake is not repeated.

## 10. The 6-request probe — and the finding that decides the verdict

Temporary patch swapping `searchProducts`' retrieval for `/shopping`; 3 scenarios × 2 reps;
`shopping.ts` restored hash-identical.

> ### ⚠️ A correction to my own measurement
> The probe's strict metric reported **0 money claims, grounded or fabricated**, across all six
> runs. That was wrong. My money regex required a unit from a fixed list and missed the form the
> model actually used — `"~7-8M"`. Re-scanned with a broader pattern, there were **5** money
> phrases. This is the fourth measurement bug I have caught in this workstream, and it would have
> produced a false "structured retrieval eliminates fabrication" conclusion.

What actually happened:

| run | verified records | money phrases in the reply |
|---|---|---|
| Sony vs Bose #1 | **0** | **`"7-8M"`** — no evidence whatsoever |
| Sony vs Bose #2 | **0** | **`"7-8M"`** — no evidence whatsoever |
| iPhone 15 vs S24 (VI) #1, #2 | 0 | none |
| EN exact model #1 | 0 | none |
| EN exact model #2 | 12 | `"11–13.3M"` (evidence: ₫10,999,000 / ₫13,299,000 — **rounded, plausibly grounded**), `"11.8–14.7M"` for iPhone, which had **no** verified records |

**With zero price evidence the model still asserted "Both are premium (~7-8M VND range in
Vietnam). Sony tends slightly cheaper".** Cleaner evidence removed the *wrong* prices; it did not
remove the *invented* ones.

This is now the same result at three consecutive layers:

| layer | intervention | outcome |
|---|---|---|
| prompt (C3-B.5) | "say you did not find a price" | fired **0/9** |
| tool payload (C3-B.6) | explicit `price_evidence: NOT_VERIFIED` | fabrication 6 → **9** |
| retrieval (C3-B.7) | remove contaminated evidence entirely | still fabricates with **0** records |

## 11. Smallest viable architecture — if the owner pursues it

1. `searchProducts` calls `/shopping` (1 call, 2 credits) instead of 3 × `/search` + image lookups.
2. A **query→product-term normalizer** strips intent words the model appends (`price`, `giá`,
   `Vietnam`, `mua`, `latest`, `best`) before identity matching. **Must be designed and proven —
   it does not exist.**
3. Deterministic identity: token containment on the normalized term + accessory lexicon rejection
   (both demonstrated to work), plus **variant handling** for the S24 class. **Also does not exist.**
4. Emit `FOUND` / `FOUND_NO_PRICE` / `NOT_FOUND` / `AMBIGUOUS` with only verified records attached.
5. Keep C3-B.5's grounding contract unchanged.

Items 2 and 3 are the real work, and §10 shows even completing them would not by itself stop the
model asserting a price when none exists.

## 12. Verdict

# OUTCOME C — RETRIEVAL REDESIGN REQUIRED

**What is required is not an external provider capability.** `/shopping` already gives structured,
merchant-attributed, product-bound prices at a third of the current cost, and it converts the
Bose total-failure case into 32 verified priced records. The gap is **internal**: a
query-normalization and variant-identity layer that does not exist, and must be built and proven
before `FOUND` / `NOT_FOUND` can be trusted.

**And a separate, larger finding the owner should weigh before funding that work:** across three
layers — prompt, payload, retrieval — the model has now been shown to assert a price whenever it
believes one is expected, regardless of what the evidence says or does not say. Improving
retrieval improves *correctness when data exists*; it has not, in any measurement so far, produced
the behaviour "say there is no price".

**Recommended next decision, not started:** treat "model asserts unverified prices" as its own
problem with its own acceptance test, rather than another retrieval iteration — because three
retrieval/prompt/payload interventions have now failed to move it.

**Preserved:** C3-B.5 remains uncommitted and intact. Nothing committed, nothing pushed, no
production file changed. Dev server stopped.
