## 3. Policies as implemented

* **R1 rounding** — `ROUNDING_TOLERANCE = 0.02`. `13.3M` verifies against ₫13,299,000; `13.8M`
  does not. A range needs **both** endpoints supported; one endpoint is never enough.
* **R2 arithmetic** — a derived difference verifies only when **both operands are already
  VERIFIED**. Two invented operands cannot manufacture a verified difference.
* **R3 redaction** — the smallest enclosing clause containing the unsupported amount is removed.
  **Every character of the output comes from the input**: no substitution, no softened rewrite, no
  new factual statement. A test asserts that literally, word by word.
* **R4 accessory requests** — the requested entity comes from the tool's own `args.query`, so
  *"đệm tai cho WH-1000XM5"* makes accessory records the **exact** target and their prices
  verifiable, while *"WH-1000XM5"* keeps them ACCESSORY. Decided from request wording, never price.
* **R5 variants** — S24 ≠ S24+ ≠ S24 FE ≠ S24 Ultra. A variant-only match returns AMBIGUOUS and is
  never upgraded.
* **R6 boundary** — no LLM call, no `toolChoice`, no prefetch, no SDK change, no cache change.

### The design decision the owner should weigh

**The guard is inert unless the evidence carries structured prices.** Today's organic retrieval
has no `price` field; treating that as "nothing is supported" would redact prices that are in fact
grounded — the opposite of the goal. So the guard enforces only where it can verify, and shipping
it changes **nothing** in production until the `/shopping` retrieval switch lands. That switch was
explicitly out of scope here (§6 says implement *only* the validator), so **this diff is safe but
also inactive on its own.** Mutation M12 locks the behaviour in both directions.

**Six survived the first run. Each was a real gap, and fixing them changed the code, not just the
tests:**

* `M08` survived because the guard returns early when nothing is unsupported — the
  "preserves a supported amount" test never reached redaction. Added a **mixed** reply where one
  claim is grounded and one is not.
* `M09` survived because `extractMoneyClaims` had its **own copy** of the masking pattern, so
  removing the URL rule from `proseOnly` left the extractor still guarding. **Refactored to a
  single shared `NON_PROSE_RE`** — a genuine duplication bug the mutation exposed.
* `M13` survived because the short-digit branch was unreachable from the existing test. Added
  `'₫'` and `'12'` cases.
* `M15`/`M16` survived because nothing tested the wiring. Added the five stream-filter integration
  tests — which also satisfy §10.
* `M06` was **my own bad mutation** (`>= 2` → `>= 0` is inert when the array is empty). Replaced
  with the meaningful one — feeding arithmetic *every* claim value — and added a test proving two
  unsupported operands cannot manufacture a verified difference.

Two implementation bugs were caught by tests before any of this: `\b\+\b` can never match, so
**"Galaxy S24+" was passing as an exact "Galaxy S24"**; and one integration test was asserting on
the whole stream, where `250.000` appears legitimately in the `a:` evidence frame — it now asserts
on the `0:` prose frames only.

## 10. Remaining risks

1. **The guard is inactive until retrieval is structured.** Shipping this alone changes nothing.
   It must land with, or before, the `/shopping` switch to have any effect.
2. **Redaction granularity.** Removal is clause-level. On a sentence with no clause delimiter the
   whole sentence goes — terser than the ideal in the brief's example, but never invents text.
3. **Attribution on multi-product sentences** returns AMBIGUOUS, which redacts. Conservative in the
   safe direction, but it can remove a grounded price stated in a two-product sentence.
4. **Fixture corpus is six turns, all Vietnamese-language requests** (T4 is an English request but
   produced no money claims). English redaction is covered by unit tests, not by a captured turn.
5. **`ACCESSORY` verdict is reachable but rare** — it fired in unit tests, not in the fixtures once
   R4 was applied.
