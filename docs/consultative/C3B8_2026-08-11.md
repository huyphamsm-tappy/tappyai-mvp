## 2. Deterministic money parser — feasible, 29/29 adversarial tests

Built measurement-only. One rule does most of the work: **a currency unit is mandatory; a bare
number is never a money claim.** That alone rejects model numbers, storage sizes, ratings,
battery hours, years, percentages and 5G.

Detects: `7 triệu` · `7,5 triệu` · `7.5 triệu` · `7–8 triệu` · `7-8M` · `7,5M` · `7m` ·
`7000000đ` · `7.000.000₫` · `7 million VND` · `$699` · `699 USD` · `699 dollars` ·
`11.8–14.7M VND` · `7.5M VND`.

Rejects: `iPhone 15 vs Galaxy S24` · `Sony WH-1000XM5` · `128GB`/`256GB` · `4.8/5 sao` ·
`pin 40 giờ` · `năm 2026` · `giảm 50%` · `5G` · markdown links and URLs containing digits ·
`[CTA_BUTTONS]` blocks · bare numbers.

**Three bugs surfaced while building it, all found by the tests, none shipped:**

* `M\b` matched **`"2 màu"` as 2 million** — JS `\b` is ASCII-only, so Vietnamese `à` reads as a
  non-word character and creates a false boundary. Every unit boundary now uses a Unicode
  lookahead `(?![\p{L}\d])`.
* `đ\b` never matched `7000000đ` for the mirror-image reason.
* `$699` was missed — `$` is the unit itself, not a prefix to one.

A fourth, self-inflicted: a `sed` edit turned `isUSD` into `/usd|dollar|$/`, where `$` matches the
empty string at end-of-input and returns **true for every unit**. Caught by inspection, fixed with
a character class. Noted because it is the same class of silent error this workstream keeps
producing.

## 3–4. Grounded-claim matching and false positives

**Corpus discipline first.** Only `c3b4-step1.json` stored full evidence **objects**
(`title`/`snippet`/`link`). `c3b3`, `c3b5` and `c3b7` stored candidate *names* or a 3-item
sample. Scoring those would have reported "no evidence" for a **capture artifact** — my first run
did exactly that and produced a headline 78/88 unverified. That number is discarded. Measured
only on the 25 replies with real evidence:

| verdict | n |
|---|---|
| VERIFIED | 10 |
| UNVERIFIED | 8 |
| ACCESSORY | 0 |
| AMBIGUOUS | 0 |
| **total money claims** | **18** across 25 replies |

**False positives — the number that matters:**

| direction | measured |
|---|---|
| **false REJECT** (a grounded claim wrongly flagged) | **0 of 18** |
| **false ACCEPT** (an unsupported claim passed as VERIFIED) | **2 of 10** |

The two false accepts are the same defect: the reply's `"18-20 million"` matched evidence text
`"iPhone 15 giá siêu hời chỉ từ 18 triệu 990"`. That is **₫18,990,000** written in the Vietnamese
compound form *"18 triệu 990"*; my parser read it as ₫18,000,000, which happened to equal the
claim's lower bound.

> **The failure is on the EVIDENCE side, parsing a price out of free-text snippet prose — not on
> the claim side.** With `/shopping`, `price` arrives as its own field and no evidence-side
> parsing is needed at all. This is the precise reason C3-B.7 and C3-B.8 belong together.

`ACCESSORY` and `AMBIGUOUS` were never triggered on this corpus — organic evidence rarely
contained a price that matched a claimed figure at all. They remain untested states.

## 6. Streaming safety

**On the turns that matter, unsupported claims do not currently reach the client early.** Any turn
that calls `search_products` sets `bufferMode`, so its prose is withheld and re-emitted whole at
`d:`/flush. The existing buffering is therefore a genuine validation window, not a race.

Turns that call **no** tool stream live — but they have no evidence to validate against, so they
need a policy decision, not a validator.

## 7. Control strategies — compared, none implemented

| | extra LLM calls | works? | risk |
|---|---|---|---|
| **A — reject / regenerate** | **+1** | yes | doubles cost per offending turn; violates the no-new-LLM-call rule |
| **B — deterministic redaction at line 495** | **0** | yes | grammar damage: removing `~7-8M` from *"Both are premium (~7-8M VND range)"* leaves a broken sentence. Safer unit is the whole sentence containing the claim, which can drop legitimate content |

| **D — pre-generation constrained evidence** | 0 | **NO — already disproven** | C3-B.7 measured the model asserting `~7-8M` with **zero** evidence records. Withholding data does not prevent the claim |

**B is the only zero-LLM-call option, and D is empirically dead.**

## 8. Cost / latency

Validation is a regex pass plus a set-membership check over ~500 tokens of text and ≤40 evidence
records: **sub-millisecond, no network, no model, no cache impact**. It runs inside an existing
transform that already awaits photo resolution, so it adds no round trip.

Current comparison path is unchanged: 2 LLM steps; `/shopping` would be ~4 credits for two
products versus ~24 today.

## 9. Proposed acceptance contract — enforceable, with one condition

> For comparison and recommendation turns, every monetary claim in the answer must be traceable to
> a matching structured evidence record. If no verified monetary evidence exists, the assistant
> must not provide a numeric price or estimate.

All eight sub-rules are deterministically checkable at the control point — **provided the evidence
carries price as a field.** Rules 1–3 (product ownership, accessories excluded, ranges only when
supported) and rule 5 (absence is valid) depend on record-level price attribution, which organic
snippets cannot give and `/shopping` can. Rule 4 (`about`/`roughly`/`~` do not relax grounding) is
free — the parser ignores hedging words entirely. Rule 7 (qualitative) stays with C3-B.5. Rule 8
(affiliate) is unaffected.
