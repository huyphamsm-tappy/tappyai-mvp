# C3-B.1 — Diagnosis of the C3-B blockers

**Date:** 2026-08-11 · **Branch:** `perf/chat-cost-phase-b` (C3-B still uncommitted)
**Type: ANALYSIS ONLY.** No production file was modified. Nothing committed, nothing pushed.

Everything below is either **VERIFIED** (a deterministic function output, a line of shipped
code, a field in the stored benchmark JSON) or **HYPOTHESIS** (stated as such, with what would
be needed to confirm it). Nothing is asserted from a single model reply.

---

## 0. Headline

The two blockers have **different** natures, and neither is what C3-B was scoped to fix.

* **BLOCKER B is architectural and now proven.** `detectForcedTool()` computes
  `search_products` for `Nên mua iPhone hay Samsung?` and the value is **thrown away** — it is
  never given to the model. `AI.stream()` never passes `toolChoice`. **There is no
  architectural bridge from `comparison` to `search_products`.** This is not a prompt issue.
* **BLOCKER A is mixed, and it is contaminated by two upstream defects** that were invisible
  until this trace: the Vietnamese question is classified as **English** before the prompt is
  even built, and on the most natural Vietnamese shopping phrasing the `search_products` tool
  is **removed from the model's tool list** by an unrelated heuristic.

And one finding that changes how the C3-B verdict itself should be read:

* **The rig could not have measured the approved objective.** `SERPER_API_KEY` is absent from
  `.env.local`, so `searchProducts()` returned its no-data fallback on **every** call in
  **both** benchmark runs. Grounded product comparison was unmeasurable on this rig regardless
  of prompt or bridge.

## 1. Scope execution trace

Traced through [route.ts](../../src/app/api/chat/route.ts) and
[promptBuilder.ts](../../src/lib/ai/promptBuilder.ts). All values below are **VERIFIED** by
running the shipped detectors on the two exact strings (Node type-strip, no re-implementation).

| Stage | `Nên mua iPhone hay Samsung?` | `Should I buy an iPhone or a Samsung?` |
|---|---|---|
| `classifyIntent` | `tool` | `tool` |
| `detectLang` | **`en`** ⚠️ | `en` |
| `detectExplicitLangRequest` | `null` | `null` |
| `detectDecisionStage` | **`comparison`** | **`comparison`** |
| `detectForcedTool` | **`search_products`** | `web_search` |
| `detectLocationIntent` | `unknown` | `unknown` |
| `detectPlanningIntent` | `null` | `null` |
| `isSimpleQuery(_, first)` | `false` | `true` |
| ⇒ `role` | `smart` | `fast` |
| ⇒ `noToolTurn` | `false` | `false` |
| ⇒ `search_products` declared? | **yes** | **yes** |
| ⇒ `langBlock` in prompt | **CRITICAL LANGUAGE OVERRIDE → English** | same |
| ⇒ `stageBlock` in prompt | `GIAI DOAN: SO SANH` | same |

Both roles resolve to the **same model** — `claude-haiku-4-5` and
`claude-haiku-4-5-20251001` in [claude.ts](../../src/lib/ai/llm/providers/claude.ts)
(`DEFAULT_MODELS`) are the alias and the pin of one model. **The role split is NOT the vi/en
explanation.** Ruled out.

**⚠️ `detectLang('Nên mua iPhone hay Samsung?') === 'en'` — VERIFIED, deterministic.**
Words = `Nên mua iPhone hay Samsung?`. Only `Nên` carries a tone mark and it is
capitalised, so `lowercaseAccentedWords = 0`; `nen`/`mua`/`hay` are all absent from
`VI_FUNCTION_WORDS` (`hay` is *deliberately* excluded, [intent.ts:83](../../src/lib/ai/intent.ts))
⇒ ratio `0/5 < 0.4` ⇒ `en`. The exact scenario the owner approved is therefore served a
prompt whose first line is *"User is writing in English. Your ENTIRE response MUST be in
English"*. The C3-B doc recorded the English refusal to a Vietnamese question as possible
n=1 variance — **it is not variance, it is a deterministic input.**
Same mechanism on `12-vi` (`Mua tai nghe bluetooth ở đâu` → `en`), which is why both runs
replied in English there, byte-identically.

## 2. Exact scope blocker

**2.1 There is no code-level scope gate.** VERIFIED: grep across `src/` finds exactly one
occurrence of the scope text — the prompt string at
[promptBuilder.ts:271](../../src/lib/ai/promptBuilder.ts). No route, middleware or guard
refuses anything. Scope is 100% model judgement.

**2.2 The refusal is not a separate step before tool selection.** VERIFIED from the stored
runs: `14-vi` and `14-en` both recorded `llmCalls = 1`, `tools = []` in **both** benchmarks.
One step, no tool call, text out. Refusing and not-calling-a-tool are the **same single model
decision**, not two stages.

**2.3 Scope is stated in four places that do not agree.** VERIFIED by reading the assembled
prompt:

| # | Location | What it says |
|---|---|---|
| 1 | `SYSTEM_BASE` line 2, `CHUYEN MON:` | **nine** domains incl. Van chuyen, Tin tuc, Thoi tiet, Gia vang |
| 2 | `NGUYEN TAC` 1–2 | always call a tool for `san pham`; else always `web_search` |
| 3 | `scopeBlock` line 1 | **"CHI ho tro 5 linh vuc"** |
| 4 | `scopeBlock` line 3 (C3-B) | shopping *includes* comparison + `nen mua iPhone hay Samsung` verbatim |
| 5 | `scopeBlock` line 4 (C3-B) | refuse `tu van cong nghe chung` |
| 6 | tool descriptions | 10 tools, four of which serve domains #3 excludes |

Statements 1 and 3 have contradicted each other since before C3-B (nine domains vs five).
C3-B added 4 and 5 — a permission and a *new* prohibition — into that same block.

**2.4 The model quotes the prohibition C3-B introduced.** VERIFIED against the stored JSON.
`14-vi` AFTER: *"TappyAI specializes in … — **not general tech advice**"*. The phrase
`tu van cong nghe chung` ("general technology consulting") **did not exist in the prompt
before C3-B** — the pre-C3-B refusal list was `toan hoc, lap trinh, y te, phap luat, chinh
tri, tin tuc thoi su quoc te, thoi tiet, cach lam gi do, dich thuat, viet lach, giai thich
khai niem`. `14-vi` BEFORE refused too, but on the generic *"nằm ngoài chuyên môn"* wording.

⇒ **HYPOTHESIS (not verified):** C3-B's permission and C3-B's new prohibition landed in the
same block, and the model resolved the pair *toward the prohibition* — supplying it with a
sharper reason to refuse than it had before. Correlation is strong (the model quotes the new
phrase almost verbatim) but this is **not** proof; only an isolated A/B on that one block —
permission alone, prohibition alone, both, neither — can establish it. That A/B is out of
C3-B's approved scope.

**2.5 Answers to the ten PART-A questions.**

1. *Which scope rule fires?* — none, mechanically. There is no rule engine; the model reads
   `scopeBlock` and decides.
2. *Which block causes the refusal?* — `scopeBlock`, evidenced by the model quoting its
   domain list. Which **clause** inside it is unproven (2.4).
3. *Does `scopeBlock` itself reject?* — it is the only text that can. It is a string, not a gate.
4. *Does another rule override the shopping permission?* — nothing *overrides* it in code.
   In text, five other statements compete with it (2.3), and one of them is the prohibition
   added by C3-B two lines below the permission.
5. *Before tool selection?* — no. Same step, same decision (2.2).
6. *Is "technology consulting" read too broadly?* — consistent with the evidence, unproven.
7. *Contradictory scope statements?* — **yes, six** (2.3), two of them pre-existing.
8. *Code-level gate outside the prompt?* — **no** (2.1).
9. *Language-specific difference?* — **yes, and it is upstream of the prompt**: the Vietnamese
   question is routed as English (1). Beyond that the two prompts differ only by `langBlock`
   and by `role` (same model).
10. *Single authoritative place?* — none exists today. `scopeBlock` is the natural candidate,
    but `SYSTEM_BASE`'s `CHUYEN MON:` line and the tool list would have to be **derived from
    it** rather than restate it. That is a change, not a finding — for owner decision.

## 3. Tool-selection execution trace

```
user request        "Nên mua iPhone hay Samsung?"
→ intent            classifyIntent            = 'tool'            (route.ts:92)
→ decision stage    detectDecisionStage       = 'comparison'      (route.ts:113)
→ forcedTool        detectForcedTool          = 'search_products' (route.ts:101)
→ …consumed by      memoryGate (106) · buildMemoryBlock (155) · telemetry log (468)
→ …consumed by      ✗ NOTHING in tool selection
→ toolChoice        never set — AI.stream() does not accept or pass it (ai.ts:56-64)
                    ⇒ SDK default 'auto'
→ available tools   9 + save_price_watch(authed only); search_products present
                    unless detectLocationIntent === 'offline'      (route.ts:340)
→ maxSteps          5                                             (route.ts:297)
→ model decision    step 1: text, no tool call
→ tool call         (none)
→ tool result       (none)
→ final response    refusal / questionnaire — ungrounded by construction
```

**Every arrow above is VERIFIED against shipped code.** Line references are exact.

1. **`detectDecisionStage` returns `comparison`** — independently re-run on the six comparison
   prompts: `05-vi`, `05-en`, `09-vi`, `09-en`, `14-vi`, `14-en` → all `comparison`. **The
   doc's claim holds.**
2. **`forcedTool`** for `14-vi` = `search_products` — the *correct* tool, computed and
   discarded. For `14-en` = `web_search` (the `\?` branch of the last regex). Neither is used
   for tool selection anywhere. The name `forcedTool` describes something the code does not do.
3. **What `route.ts` passes to the model:** `model`, `messages`, `maxTokens`, `maxSteps`,
   `tools`, `onFinish`, `abortSignal` — that is the complete argument list of
   [ai.ts:56-64](../../src/lib/ai/llm/ai.ts). **No `toolChoice`. No forcing mechanism. No
   preparation/step mechanism.** `toolChoice` is not even a field on `AIStreamOptions`.
4. **Is there any mechanism translating `comparison` → `search_products`?**

   > **There is no architectural bridge.** `decisionStage` has exactly two consumers:
   > `noToolTurn` (only for `'confirmation'`) and the `stageBlock` **text** passed to
   > `buildSystem`. It never touches the tool set, tool choice, or any pre-fetch.

   This is not a prompt issue and must not be reported as one.
5. **`toolChoice` is `auto` ⇒ the model is simply choosing not to call the tool.** VERIFIED
   and *documented*: on the six comparison scenarios the model called tools when it judged it
   needed data (`09-en`: `get_hotel_prices` ×2, both runs) and did not when it judged it did
   not (`05`, `14`, both languages, both runs). Prompt text asking for grounding does not
   change a decision the model makes before reading any data.

**Additional VERIFIED tool-availability defect (not in the original blocker list).**
`detectLocationIntent` returns `'offline'` for `Mua tai nghe bluetooth ở đâu` (matches
`\bo\s+dau\b`) and for both `05` prompts (`\bpho\s+[a-z]` — the street word *phố* matching the
dish *phở*, and matching English `"Pho or …"` too). When it is `'offline'`,
[route.ts:340](../../src/app/api/chat/route.ts) **removes `search_products` from the tool set
entirely** and the prompt adds *"TUYỆT ĐỐI KHÔNG dùng search_products"*. So on the most
natural Vietnamese shopping phrasing — *"mua X ở đâu"* — the shopping tool is not merely
unforced, **it is not offered**. That matches the stored data exactly: `12-vi` called **no
tool at all** in both runs while `12-en` called `search_products`.

## 4. Exact point where comparison fails to reach `search_products`

**[route.ts:113](../../src/app/api/chat/route.ts).** `decisionStage` is assigned, and from
there the only paths out are a boolean for `'confirmation'` and a string appended to the
prompt. The value never reaches `tools`, never reaches `toolChoice`, and there is no
pre-fetch. The failure point is an **absent edge in the data flow**, not a weak instruction.

## 5. Does a comparison→tool bridge exist?

**No.** See §3.4. Verified by exhaustive grep of both consumers of `decisionStage`.

## 6. Why the option count is not narrowed — and why "6→11" does not mean what it looks like

**The metric does not measure options.** `boldSpans` counts every `**…**` span
([consultativeBench.test.ts:87](../../src/lib/ai/__measure__/consultativeBench.test.ts)).
`SYSTEM_BASE`'s style rule tells the model to bold **place names, product names AND prices**,
and C3-B's R1(c)/(f) explicitly ask for more per-option evidence (ratings, distance, opening
hours, price, source). More evidence ⇒ more bold spans, with the option count unchanged.

The stored `ungroundedBold` fields settle it — these are the "options" the metric counted:

* `13-vi` AFTER: `["JBL, Sony, Anker, Soundcore", "true wireless (không dây hoàn toàn)", "chụp tai", "cổ vòng"]` — a brand list and three **answer choices inside a question**.
* `15-vi` AFTER: `["Tai nghe không dây", "có dây", "Ngân sách", "Mục đích chính"]` — **bolded question labels**.
* `17-vi/en`: the five TappyAI domains.

⇒ **`boldSpans` is not an option count, and "2–4 did not narrow" is not established by this
evidence.** It also moved *up* in Vietnamese from a floor of zero (`01/02/03-vi`: 0→3, 0→3,
0→4), which a narrowing failure cannot explain.

**Is narrowing prompt-only or does it need deterministic candidate shaping?** The evidence
points at shaping, for a reason independent of the prompt: `searchProducts()` returns up to
**8** de-duplicated results ([shopping.ts:44](../../src/lib/ai/tools/shopping.ts)) with **no
ranking**, and `search_places` returns 10 (`toolNamesReturned = 10` in the stored runs). The
prompt asks the model to both *rank* and *cut* an unranked list on every turn. No code ranks
or truncates candidates before generation. Establishing this properly needs a run where the
tools actually return data — which, per §8, this rig cannot do.

## 7. Why the English comparison became a questionnaire

`14-en` AFTER: `clarifications = 8`, `tools = []`, `llmCalls = 1`. Candidate causes, weighed
against what is actually in that request's prompt:

| Candidate | Verdict |
|---|---|
| Scope | **Ruled out for `14-en`** — it stopped refusing; it engaged with the question. |
| Missing tool result / missing product data | **Consistent.** No tool was called, so the model had literally nothing to compare (§3). |
| Clarification logic | **Not code.** `countClarificationQuestions` is measurement-only — "nothing in the request path calls this" ([clarification.ts](../../src/lib/ai/clarification.ts)). The one-question ceiling exists only as prompt text (R7). |
| Comparison-stage interaction | **Consistent, and C3-B-introduced.** The comparison `stageBlock` now *ends* with `"Neu uu tien cua user chua ro, hoi DUNG MOT cau ngan de chot"` — the **last line** of that block is an instruction to ask. With no data and no stated preference, the model lands on exactly that branch. |
| Existing rule conflict | **Consistent.** R7(c) also routes "missing decision information" to a question; the one-question cap is a separate sentence in a different rule. |
| Model uncertainty | Consistent, unmeasurable here. |

**HYPOTHESIS (not verified):** with zero data in context, C3-B's comparison block and R7(c)
both terminate in "ask", and the ceiling that limits it to one question sits elsewhere in the
prompt. This predicts the *Vietnamese* regressions too, and they are in the stored data:
`05-vi` went from a real comparison (2 bold, trade-off present) to a **pure question** (1
bold, no trade-off), and `09-vi` from a 3-option comparison to **two questions and zero
options**. Same shape, same direction, both languages. Not proof — the isolating experiment
is a run with the `NGHIENG VE`/"hoi DUNG MOT cau" line removed.

## 8. ⚠️ The rig could not measure the approved objective

**VERIFIED, and this bounds every conclusion above.**

* `.env.local` — the only env file `next dev` loads here — contains **no `SERPER_API_KEY`**
  (12 keys; `SERPER` appears only in `.env.production.local`, which Next.js does **not** load
  in development).
* `serperSearch()` returns `null` immediately without the key
  ([common.ts:296-298](../../src/lib/ai/tools/common.ts)).
* `searchProducts()` therefore always takes its fallback branch — `{ note, links,
  shop_info_results: [] }`, **no `search_results`** ([shopping.ts:69-75](../../src/lib/ai/tools/shopping.ts)).
* The stored runs agree: **every** `search_products` call in **both** benchmarks returned
  `toolNamesReturned = 0` (`12-en`, `13-vi`, `13-en`). By contrast `search_places` returned 10
  names and `get_hotel_prices` 6 — those come from OSM and need no Serper key.

⇒ The three product replies list **Shopee / Tiki / Lazada** as their "options" because that is
the entire fallback payload. **A grounded product comparison was impossible on this rig even
if the bridge had existed.** The approved objective — "grounded in `search_products` results"
— was never testable in either run.

**Second rig defect.** The benchmark's `stage` column is computed on
`detectDecisionStage(turn.text, …)` where `turn.text` is the **assistant's reply**
([consultativeBench.test.ts:92](../../src/lib/ai/__measure__/consultativeBench.test.ts)). It
is not the request's stage. That is why `16-en`, `17-en` and `13-en` show `stage=comparison`
and `05-en` shows `stage=null`. Anyone reading that column as "which stage fired" is reading
noise. (The C3-B doc's stage claim was made *separately* and is correct — §3.1 re-confirms it
— but the column itself is unusable.)

## 10. Smallest viable architectural fix

Ranked by cost-to-risk. **Proposals only — none implemented.**

**A. Bridge `comparison` → data by PRE-FETCHING server-side, not by forcing the model.**
Before `AI.stream`, when the turn is a shopping-shaped comparison, call `searchProducts()` on
the server and inject the (already slimmed) result into `dynamic`. The model then *has* the
data instead of being told to go get it. No forcing, no SDK risk, no second generation pass.
Open question that must be answered before this is buildable: how the two compared items are
extracted from `"A hay B"` deterministically. That extraction is the real work.

**B. Fix the two upstream defects that make the approved scenario unreachable.**
`detectLang` on `Nên mua iPhone hay Samsung?`, and the `locationIntent === 'offline'` gate
that deletes `search_products` on `"mua X ở đâu"`. Both are small, both are VERIFIED, both are
currently filed under other phases (C5 / none). Neither is a prompt change.

**C. Give `scopeBlock` a single authority.** Only after an isolated A/B establishes which
clause actually produces the refusal (§2.4). Doing it before that is guessing.

**D. Restore the rig before re-measuring anything.** Serper key for the dev server (owner
decision — it is a paid quota: note `searchProducts` issues **three** Serper queries per call,
plus up to 8 image lookups), `stage` computed on the request, and an option count that is not
`boldSpans`. Without D, a C3-B.2 re-run produces numbers of the same quality as C3-B's.

## 11. Can the fix preserve one LLM call?

| Approach | LLM calls | Verdict |
|---|---|---|
| **A — server-side pre-fetch** | **Fewer than today's tool path.** A tool call costs 2 steps (call + answer); pre-fetch costs **1**. | ✅ can be cost-**negative** |
| `toolChoice: 'required'` or `{type:'tool'}` | Would loop to `maxSteps` = 5 | ❌ see §12 |
| Second classification/generation pass | +1 call per turn | ❌ violates the finalized cost constraint |
| AI SDK 5 upgrade for `prepareStep` | 1 | ❌ out of scope, and the C2 note warns an upgrade silently switches forcing on |

**PART C answer — is there a safe supported mechanism in the CURRENT SDK?**
**No, for forcing. Yes, for pre-fetching (which needs no SDK feature).**
VERIFIED in the installed `ai@4.3.19`: `experimental_prepareStep` is destructured at
`dist/index.mjs:4177` inside **`generateText` only**. `streamText` destructures `toolChoice`
at `:5196` and applies it inside `streamStep` at `:5654-5656` via
`prepareToolsAndToolChoice({ tools, toolChoice, activeTools })` — using the **outer** constant,
**re-applied identically on every step**, with no per-step override. Setting a forced
`toolChoice` therefore forces a tool call on step 2, 3, 4 and 5 as well: the run consumes
`maxSteps` and never emits a text answer. That is the same failure class as the `maxSteps: 1`
chitchat bug already fixed this sprint (empty reply). **This is the "accidental global
forced-tool behavior" the brief warned about, and it is confirmed, not theoretical.**

⇒ Per the brief: **forcing is an architectural decision requiring the Owner.** No speculative
mechanism was implemented.

## 12. Risks

* **Forcing a tool** — loops to `maxSteps`, empty reply, 5× cost. Confirmed mechanism (§11).
* **Pre-fetching (A)** — burns 3 Serper queries per comparison turn even when the model
  wouldn't have searched; adds one round trip of latency; adds input tokens. Those tokens land
  in `dynamic`, **after** the cache breakpoint, so the 11k shared prefix is **not** invalidated
  — B1 stays intact.
* **Opening the scope (C)** — the prohibition exists for a reason; loosening it without the
  A/B risks the model answering genuinely out-of-scope technology questions.
* **`detectLang` (B)** — it has already been broken in both directions twice (documented in
  [intent.ts:89-103](../../src/lib/ai/intent.ts)). Any change needs the existing corpus plus
  the new cases, or it re-opens a shipped bug.
* **Re-measuring with a Serper key** — behaviour will change substantially once product data
  actually arrives. C3-A/C3-B numbers are **not** a valid baseline for a keyed run.
* **Reading this report as a fix plan** — six of the thirteen findings are hypotheses. Two
  isolating experiments (§2.4, §7) are needed before any prompt change is justified.

## 13. Recommended C3-B.2 scope — proposal, awaiting owner approval

Ordered so that each step's result decides whether the next is worth doing.

1. **Restore measurement (§8).** Serper key on the dev server (owner-only), `stage` computed
   on the request, option count that is not `boldSpans`. *No production code.*
2. **Re-baseline** the six comparison scenarios with data actually flowing. Several of the
   C3-B "failures" may not survive this. n≥3 on those six only.
3. **Fix the two verified upstream defects (§10-B)** — `detectLang` and the `locationIntent`
   gate — test-first, RED before GREEN. These are the smallest changes with the largest
   verified effect, and they need no prompt edit.
4. **Then, and only then, the two isolating A/Bs** — `scopeBlock` permission-vs-prohibition
   (§2.4), and the comparison block's trailing "ask" line (§7).
5. **Then decide on the bridge (§10-A)** with real numbers in hand.

**Not proposed:** forcing `toolChoice`, an SDK upgrade, a second LLM call, any new prompt
wording. **Not touched:** Cost Optimization, B1/B2/B4/B6/B7, C1, C2, C2.1. **Not started:**
C3-C, C4, C5, C6.
