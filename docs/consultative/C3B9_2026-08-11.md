the B7-A photo pass found every record pre-enriched and spent **zero** extra credits.

Also `161k`, which rounds from an accessory record at ₫161,241, was **not** verified.

> **Accessory false accepts: 0.** An accessory price can no longer pass as a product price.

**Nuance the owner should note:** on T5 the *user asked about* ear pads, so quoting them is
correct behaviour. The validator judges the price against the product entity and has no notion of
"the request was about the accessory". A naive redaction policy would strip correct content here.
This is a bounded policy gap, not a matching error.

## 7. Range results

Strict rule applied, no tolerance: a range verifies only when **both** endpoints exactly equal
`EXACT_PRODUCT` prices in the same turn's evidence.

* `6.49 - 8.09 triệu` → **VERIFIED** (both endpoints present).
* `12.3–18.5 million`, `9.5–13.3 million`, `11.3–13.3 million` → **UNVERIFIED**. Each is the model
  *rounding* a real figure (₫18,490,000 → "18.5M"; ₫13,290,000 → "13.3M"; ₫13,299,000 → "13.3M").
  The rounding is annotated in the output but **never upgrades a verdict**.
* `2–5 million`, `2–3 million` → **UNVERIFIED**. These are *derived difference* claims ("cheaper
  by…"), not quotable prices; no record can support them.

The three bounded cases are all **policy questions, not validator errors**:

1. **Rounded figures** (3 claims) — the model writes "13.3M" for ₫13,299,000. Strictly unverifiable
   at the digit level; the owner must decide whether rounding to 3 significant figures is
   acceptable grounding.
2. **Derived differences** (2 claims) — "cheaper by 2–5 million" is arithmetic over two records.
   Verifiable only if the validator is allowed to compute differences.
3. **Accessory-topic turns** (T5) — correct content flagged because the entity is the product.

**Sample size is small and stated as such: 16 claims, 6 turns, one language mix.** This is a
feasibility proof, not a statistical benchmark.

**One measurement artifact was found and fixed, and is reported rather than buried:** the first
scoring pass returned AMBIGUOUS for grounded claims on single-product turns whenever the sentence
did not repeat the model name (*"Giá dao động 6.49–8.09 triệu"*). On a single-entity turn there is
only one product a price can refer to. Fixing that moved 3 claims from AMBIGUOUS to VERIFIED and
2 to ACCESSORY. The C3-B.8 parser itself was **not** modified — its 29/29 suite re-ran green.

## 9. Control-point verification

Confirmed by reading the code and by the capture itself — **not modified**:

1. **Complete text available** — `mainText` accumulates every `0:` chunk while `bufferMode` is set.
2. **Structured records available** — the filter builds records as
   `searchResults.map(r => ({ ...r, name: … }))`; the spread preserves `price`, `source`,
   `productId`. The capture read those exact fields out of the `a:` frames, so this is
   demonstrated rather than assumed.
3. **Validation can run before emission** — the last write is
   `controller.enqueue('0:' + JSON.stringify(finalText))` in `emitReconstructed()`.
4. **Structured blocks must be scrubbed** — `mainText` contains the inline `[CTA_BUTTONS]`,
   `[FOLLOWUPS]` and `[TAPPY_PLAN]` text. The parser already strips all three plus markdown links
   and URLs; without that, marketplace URLs containing digits would be parsed as prices. This is a
   hard requirement on any implementation.
5. **No client change** — `search_results` appears in zero Kotlin/Java/Swift/TSX source files.

## 10. Streaming safety

`PLACE_TOOLS` includes `search_products`, so on every turn measured here the prose was **withheld**
and re-emitted whole. `emitReconstructed()` is the first point at which the complete prose exists,
and it is server-side and pre-emission. **Validation there would prevent an unsupported price from
reaching the client.** Turns that call no tool stream live — they have no evidence, so they need a
policy decision, not a validator. Streaming was not modified.
