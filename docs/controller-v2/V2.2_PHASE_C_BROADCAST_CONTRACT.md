## 1. The question that decides everything: users or devices?

**The broadcast addresses PEOPLE. Delivery reaches devices as a consequence.**

One notification row per recipient (the Inbox entry), and a push to each device that recipient currently owns. A person with a laptop and a phone gets **one** inbox row and **two** pushes — because they asked to be notified on two devices, not because they were counted twice.

This must be stated because the two readings produce different systems, and the existing code reads one way while the risk register reads the other.

### 1.1 Why `user_id` deduplication is correct — and why that is not obvious

`getAllSubscribedUserIds()` ends with:

```ts
return Array.from(new Set((data ?? []).map(r => r.user_id as string)))
```

It deduplicates by **user id**, never by credential. Read alone, that looks like the classic fan-out bug: if one device were claimed by three accounts, a broadcast would push to that device three times, and the person holding it would receive two notifications addressed to strangers.

**That cannot happen, and the reason is a database invariant, not this function.** Since `20260830_push_credential_ownership.sql`:

| | Invariant | Enforced by |
|---|---|---|
| **I1** | at most **one enabled row per credential** | partial unique index `WHERE enabled` |
| **I1′** | subscribing **transfers** ownership atomically | `BEFORE` trigger inside the upsert's own statement |

Given I1, iterating distinct users and sending to each user's enabled subscriptions visits **every credential at most once**. User-level dedup is therefore credential-safe *as a consequence of I1*, not on its own merit.

> 🚨 **This is a load-bearing dependency, and it is invisible at the call site.** Anyone who relaxes I1 — drops the partial unique index, widens it, adds a second enabled row per credential for any reason — silently converts every broadcast into a per-device fan-out with cross-account delivery. That is the 2026-08-29 incident again, multiplied by the whole subscriber base.
>
> **Requirement C-1.** The broadcast implementation must carry a test that fails if I1 is not enforced — not a comment. It asserts the behaviour: two enabled rows for one credential must be impossible, and the audience builder must visit that credential once.

### 1.2 What is NOT decided by this

Per-device targeting, "send to this person's phone only", and per-device opt-out are **out of scope**. `notification_subscriptions` is `UNIQUE(user_id, provider)` — one account holds at most one webpush row today — so per-device semantics do not exist to be expressed yet.

### 1.3 What broadcast relies on I1′ for, and what it must never do

**I1′** — a new enabled registration **transfers** ownership atomically, inside the upsert's own statement — is what makes a materialised audience trustworthy for the length of a send. Without it there is a window in which a credential has two enabled owners, and any audience snapshot taken during that window fans out across accounts.

**Requirement C-20.** Broadcast **reads** ownership and never writes it. It must not disable, re-own, prune-by-ownership or "repair" a subscription as a side effect of sending. Pruning a `gone` endpoint stays where it already is, in `send.ts`.

> 🚨 **The audience function is NOT dead code, and this changes what may be done to it.** MEASURED on `origin/main`: `getAllSubscribedUserIds()` is called by **`/api/cron/deal-notifications`**, which **is** registered in `vercel.json` and runs daily at 00:30 UTC. Editing that function in place to serve broadcast silently changes a live daily job that notifies every subscribed user about deals.
>
> **Requirement C-21.** Phase C introduces its **own** audience builder. It does not modify `getAllSubscribedUserIds()`, and a test pins the deal cron's audience behaviour so a future refactor of one cannot quietly redefine the other.

> ⚠️ **And there are two seam-bypassing paths, not one.** `/api/cron/deal-notifications` also calls `emitNotification` per user directly under `Promise.allSettled` — no cap, no dedupe, no audit record — exactly the shape §14 describes for the legacy broadcast route. Retiring the legacy route alone would not close the pattern. **This contract does not change the deal cron**; it records that O-4's real subject is a *class* of path, and that a second decision may be needed later. That is noted, not smuggled in.

## 2. Audience

**Audience = every user with at least one enabled subscription, at the moment the send starts.**

| Question | Answer |
|---|---|
| Users with no subscription | **Excluded from push. Open question O-1: do they still get an inbox row?** |
| Users with a disabled subscription | Excluded. `enabled = false` is the person's own "no", or a transfer, or a pruned dead endpoint — all mean *do not push* |
| Anonymous sessions | **Excluded.** They are `auth.users` rows and can hold subscriptions; a broadcast is a message to members. Requirement **C-2**: the audience query excludes `is_anonymous = true`, with a test |
| Suspended / banned accounts | **Open question O-2.** Module 08 has account status; nothing currently filters an audience by it |
| Snapshot vs live | The audience is **materialised once** at the start. A person who subscribes mid-send is not in this broadcast |

### 2.1 Push and inbox are two deliveries — 🔴 **BLOCKED — O-1**

**Measured, so the decision is made against facts and not against a guess:**

- `emitNotification` **always writes the `notifications` row first**, then attempts push. With no subscription: `attempted = 0` → `push_status = 'skipped'`. The inbox row exists regardless.
- The legacy broadcast route nevertheless **iterates only subscribed users**, so today a person who never enabled push receives **nothing at all** — not even an inbox row.
- 🚨 **There is no notification preference in the product.** Nothing separates "I want the bell in the app" from "I want a push on my phone". The only signal that exists is the push subscription.

That last point is why this cannot be answered by picking the nicer-sounding option:

| | Option | What it actually means, given that there is no preference |
|---|---|---|
| **A** | inbox row for **every** user | Reaches everyone who opens the app. **But the only "no" a person has ever been able to express is turning off push** — so this delivers to people who used the one refusal available to them. That is a defensible product choice; it is not a neutral one |
| **B** | only subscribed users | Today's behaviour, and honest about consent. Audience = **1** in production right now |

**Requirement C-22.** Whichever is chosen, the answer is written down **as the definition of three separate concepts** — *push opt-in*, *inbox row*, *notification preference* — and whether they are one thing or three. If they are three, the product does not yet have the second and third, and that is a follow-up decision, not something Phase C invents.

### 2.2 Suspended and banned accounts — 🔴 **BLOCKED — O-2**

**Measured:** account status exists (Module 08) and **no audience query filters on it anywhere.**

| | Option | Cost |
|---|---|---|
| **A** | excluded from the audience entirely | Cleanest. A wrongly-suspended person also stops receiving service notices |
| **B** | included | Sends announcements, possibly marketing, to accounts the platform has banned |
| **C** | no push, inbox row only | Coherent for a service notice — including the notice *about* the suspension. **Only expressible if O-1 = A**; if O-1 = B there is no inbox-only delivery to select |

> 🚨 **O-1 and O-2 are not independent, and choosing B for O-1 silently removes option C from O-2.** Please answer O-1 first.

### 2.3 Subscription semantics — ⏸ partial, pending O-1

Fixed regardless of O-1, because these follow from I1/I1′ rather than from product choice:

- `enabled = false` means **do not push**, in every case — a person's own refusal, an ownership transfer, and a pruned dead endpoint are indistinguishable at send time and must be treated identically.
- A user with **no row at all** and a user with a **disabled row** are the same for *push* purposes. Whether they are the same for *inbox* purposes is precisely O-1.
- Anonymous sessions hold real subscriptions and are **excluded** (C-2) — settled, not open.

## 3. Authorization

| | |
|---|---|
| Permission | **`notifications.send.broadcast`** — already in the canonical registry |
| Roles | **`super_admin` only** |
| Implied by `notifications.send.user`? | **NO — deliberately, and this must never be "simplified"** |
| Owner | reaches it through `Actor.isOwner`, the existing constitutional bypass. **No email is read anywhere** |

The role ladder here is rank-based with inheritance, so "admin can do everything below super_admin" is the default expectation and this exception **will be eroded by accident** unless it is pinned.

**Requirement C-3.** A test asserts an `admin` actor holding `notifications.send.user` is **refused** `notifications.send.broadcast`. Behavioural, through the PDP, not a registry-shape assertion.

**Requirement C-4.** The route calls `requirePermission` itself. The page deciding not to render a button is not authorization — the same rule `/admin/notifications` already states in its own header.

**Requirement C-5.** `dispatchService.ts` keeps **zero authorization primitives**. It is the shared seam for Controller *and* Marketing; putting a permission check inside it would make the two callers' authorities imply one another. The caller authorizes, then hands over an already-authorized recipient list.

**Requirement C-6.** No service-role in the user-facing route. No RLS change.

## 4. The cap is a design decision, not a detail

```ts
export const MAX_RECIPIENTS_PER_DISPATCH = 500
```

The seam refuses more than 500 recipients per dispatch, and it owns that cap so neither caller can exceed it.

**A broadcast to "everyone" therefore does not fit through the seam the moment the subscriber base passes 500.** Production has **one** enabled subscription today, so this would not bite for a long time — which is exactly why it must be decided now rather than discovered later.

**Open question O-3 — three ways out, and they are not equivalent:**

| Option | What it means |
|---|---|
| **A. Keep the cap, chunk the send** | Broadcast becomes N dispatches of ≤500. Needs a job, resumability, and a partial-failure story. The cap keeps protecting Marketing |
| **B. Raise the cap for broadcast only** | A second, larger cap the seam knows about. Simpler, but the number stops meaning "the most anyone can send at once" |
| **C. Broadcast bypasses the seam** | ❌ **Rejected in this draft.** It would duplicate fan-out, result aggregation and audit — the exact divergence the seam exists to prevent, and the existing `/api/notifications/broadcast` already demonstrates that failure mode by writing no audit record at all |

Recommendation: **A**, and the chunking belongs to the broadcast caller, not the seam. **A recommendation is not a decision — O-3 is still the Owner's.**

**Requirement C-23.** No path may call an internal dispatch function to get around the cap. Every dispatch, on every option, is **≤ 500**.

### 4.1 Deterministic ordering — ✅ decided by necessity, and **today's code does not satisfy it**

🚨 **MEASURED — this is a real gap, not a hypothetical.** The audience query is:

```ts
.from('notification_subscriptions').select('user_id').eq('enabled', true)
```

**There is no `ORDER BY`.** PostgreSQL is free to return those rows in any order, and it changes in practice — after an update, a vacuum, a plan change from seq-scan to index-scan. `new Set(...)` then preserves whatever arrival order it was given.

Why that is fatal to a resumable chunked send, independent of which option O-3 takes: "chunk 3 of 12 failed, resume from chunk 3" is meaningless if re-running the query yields a **different chunk 3**. Some people get the message twice, others never.

**Requirement C-24.** The broadcast audience is **totally ordered by a stable key** — `user_id` ascending is sufficient and needs no new column — and the ordering is applied **in the query**, not in JavaScript after the fact, so it survives pagination.

**Requirement C-25.** A test asserts the same audience, queried twice, yields the **same sequence** — not the same set. A set-equality assertion would pass against exactly the bug this prevents.

> This requirement holds under **A**, **B** and any option C. It is listed as decided because it is not a preference — without it, no resumable or idempotent broadcast is possible at all.

### 4.2 Chunking — 🔴 **BLOCKED — O-3**

Written only if O-3 = **A**. When it is, this section must fix, in writing and before code: chunk size (≤ 500) · the stable ordering from §4.1 · where run state lives so a resume knows what completed · retry policy per chunk, with a bound · what a chunk that fails **after** dispatch but **before** its state is recorded does (the only genuinely hard case — it is why C-7's idempotency key must be per **recipient**, not per run) · cancellation mid-run (C-13) · and the audit record's relationship to chunks: **one record per broadcast**, not one per chunk (C-15).

If O-3 = **B**, this section is replaced by: the second cap's value, why that number, who may use it, and the test that pins Marketing to the original 500.

## 5. Idempotency, retry and partial failure

**Idempotency today** is a 60-second sha256 fingerprint in the seam (`distributedRateLimit`). That is duplicate *suppression* for a double-clicked button — it is **not** an idempotency key, and it must not be described as one.

**Requirement C-7.** A broadcast carries an explicit **idempotency key**, supplied once and reused across chunk retries, so a resumed job cannot re-notify the people it already reached.

**Failure semantics, stated honestly** — the vocabulary is already fixed by the send path and must not drift:

| Term | Meaning |
|---|---|
| `accepted` | the push service accepted it. **NOT "the device displayed it"** |
| `failed` | transient error, retry-worthy |
| `gone` | 404/410 — the endpoint is permanently dead; `send.ts` prunes it by setting `enabled = false` |
| `unreachable` | the recipient had no enabled subscription |

> 🚨 **The word "delivered" is forbidden**, and there is already a test that fails on it. Neither Web Push nor FCM confirms display.

**Requirement C-8.** Partial failure is reported per chunk and in aggregate, and a broadcast that fails halfway says **which recipients were reached**, not just a count.

**Requirement C-9.** The `push_status` `gone → sent` defect is a **known, Owner-deferred** bug. This contract does not fix it and does not depend on it. If broadcast reporting would make it visible at scale, that is a reason to raise it with the Owner — not to quietly fix it inside this work.

## 6. Stale credentials

A credential can be stale in two different ways, and only one is handled today:

1. **Dead** — the push service answers 404/410. `send.ts` prunes it. ✅ handled
2. **Wrong owner** — the browser now belongs to somebody else. Closed for the *login* path by **I2** (`/api/notifications/subscribe/reconcile`), verified in production on 2026-08-30.

**Requirement C-10.** Broadcast changes neither. It must not "repair" ownership as a side effect of sending: a send path that mutates ownership is a send path that can be used to mutate ownership.

## 7. Rate limiting and abuse

**Requirement C-11.** A broadcast-specific limit, distinct from the per-actor admin limiter. The relevant unit is **broadcasts per day**, not requests per minute — the harm is one unwanted message to everyone, not a burst.

**Requirement C-12.** **Dry run first.** The route supports a mode that resolves the audience, writes the audit record, and sends **nothing**, returning the count and the sample it would have reached. This is how the first real broadcast gets reviewed before it exists.

**Requirement C-13.** **Kill switch.** A way to stop an in-flight chunked broadcast, and a way to disable the surface entirely without a deploy.

**Requirement C-14.** **Two-step confirmation** in the UI, showing the resolved audience count from the dry run. Typing a confirmation phrase, not a second button.

---

## 8. Audit, logging and privacy

**Requirement C-15.** One audit record per broadcast, through `writeAuditLog`, carrying the actor, the origin (`'controller'`), the action, the audience size and the idempotency key.

**Requirement C-16.** **No recipient identity in the audit record** — the existing dispatch audit already records the actor only, and that is deliberate.

**Requirement C-17.** **No raw push endpoint or FCM token in any log, error, response body or URL.** Where a credential must be identified, use 8 hex characters of its sha256. An endpoint names one person's browser; it does not by itself allow sending a push — that needs the VAPID private key and the subscription's encryption keys — but it is the single input that can silence that device.

---

## 9. Observability

**Requirement C-18.** A broadcast reports, per run: audience size · chunks · accepted · failed · gone · unreachable · duration. Aggregate counts only.

**Requirement C-19.** `gone` counts are expected to be non-zero and are **not** a failure signal — they are the prune working.

## 11. Rollout

2. Implementation + tests, no send path enabled

### 11.1 Rollback and operational behaviour

**A sent broadcast has no rollback.** That is the premise of this whole document, and it is why the controls sit *before* the send: dry run (C-12), two-step confirmation (C-14), kill switch (C-13).

What **can** be rolled back, and must be, per layer:

| Layer | Rollback |
|---|---|
| Code | Ordinary revert. The feature ships **disabled**; the first deploy changes nothing observable |
| Surface | C-13's kill switch disables it **without a deploy** — the reason it is a requirement and not a nice-to-have |
| In-flight run | Cancellation stops **subsequent** chunks. Recipients already dispatched to are already reached, and the run report must say so plainly rather than reporting the run as "cancelled" |
| Inbox rows | Deleting rows already read is not a rollback, it is a second surprise. **Out of scope** — if a broadcast must be retracted, that is a product decision needing its own contract |
| Schema | Phase C introduces **no migration**. If that stops being true, the migration ships with a rollback file, per the repo's existing practice |

**Requirement C-26.** The feature is behind an off-by-default switch from the first commit, so that merging, deploying and enabling are three separate acts.

## 13. Multilingual behaviour — 🔴 **BLOCKED — O-5**

**Measured:** `notifications` stores **one `title` and one `body`**. A grep of the notification migrations for `locale` and `lang` returns **0 hits** — there is no per-row language, and `emitNotification` takes one title and one body. The platform ships EN/VI.

| | Option | What it costs |
|---|---|---|
| **A** | one message for everyone | Nothing to build. Roughly half the audience is addressed in a language they did not choose |
| **B** | per-user locale | Needs a **server-side** source of each user's language. ⚠️ **Unaudited** — the web app resolves language client-side from `localStorage` (`tappy_lang`), and whether a server-readable per-user locale exists at all is **not established**. If O-5 = B, the first step is that audit, and it may conclude the data does not exist yet |
| **C** | campaign carries translations | The sender supplies EN + VI; delivery picks per recipient, falling back to one. Still needs B's locale source to *pick*, so **C does not avoid B's audit** — it only moves who writes the copy |
| **D** | something else | — |

**Requirement C-27.** No schema is added for this until O-5 is answered. If B or C, the locale-source audit happens **before** any design, and its result is recorded here — including "it does not exist", which is a legitimate outcome that changes the answer.

> 🔑 **C is not a way to dodge the audit.** Both B and C need to know a recipient's language at send time. Only A does not.
