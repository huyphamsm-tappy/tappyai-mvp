## 1. The question that decides everything: users or devices?

**The broadcast addresses PEOPLE. Delivery reaches devices as a consequence.**

One notification row per recipient (the Inbox entry), and a push to each device that recipient currently owns. A person with a laptop and a phone gets **one** inbox row and **two** pushes — because they asked to be notified on two devices, not because they were counted twice.

This must be stated because the two readings produce different systems, and the existing code reads one way while the risk register reads the other.

### 1.1 Why `user_id` deduplication is correct — and why that is not obvious

`getAllSubscribedUserIds()` ends with:

```ts
return Array.from(new Set((data ?? []).map(r => r.user_id as string)))
```

It deduplicates by **user id**, never by credential. Read alone, that looks like the classic fan-out bug: if one device were claimed by three accounts, a broadcast would push to that device three times, and the person holding it would receive two notifications addressed to strangers.

**That cannot happen, and the reason is a database invariant, not this function.** Since `20260830_push_credential_ownership.sql`:

| | Invariant | Enforced by |
|---|---|---|
| **I1** | at most **one enabled row per credential** | partial unique index `WHERE enabled` |
| **I1′** | subscribing **transfers** ownership atomically | `BEFORE` trigger inside the upsert's own statement |

Given I1, iterating distinct users and sending to each user's enabled subscriptions visits **every credential at most once**. User-level dedup is therefore credential-safe *as a consequence of I1*, not on its own merit.

> 🚨 **This is a load-bearing dependency, and it is invisible at the call site.** Anyone who relaxes I1 — drops the partial unique index, widens it, adds a second enabled row per credential for any reason — silently converts every broadcast into a per-device fan-out with cross-account delivery. That is the 2026-08-29 incident again, multiplied by the whole subscriber base.
>
> **Requirement C-1.** The broadcast implementation must carry a test that fails if I1 is not enforced — not a comment. It asserts the behaviour: two enabled rows for one credential must be impossible, and the audience builder must visit that credential once.

### 1.2 What is NOT decided by this

Per-device targeting, "send to this person's phone only", and per-device opt-out are **out of scope**. `notification_subscriptions` is `UNIQUE(user_id, provider)` — one account holds at most one webpush row today — so per-device semantics do not exist to be expressed yet.

### 1.3 What broadcast relies on I1′ for, and what it must never do

**I1′** — a new enabled registration **transfers** ownership atomically, inside the upsert's own statement — is what makes a materialised audience trustworthy for the length of a send. Without it there is a window in which a credential has two enabled owners, and any audience snapshot taken during that window fans out across accounts.

**Requirement C-20.** Broadcast **reads** ownership and never writes it. It must not disable, re-own, prune-by-ownership or "repair" a subscription as a side effect of sending. Pruning a `gone` endpoint stays where it already is, in `send.ts`.

> 🚨 **The audience function is NOT dead code, and this changes what may be done to it.** MEASURED on `origin/main`: `getAllSubscribedUserIds()` is called by **`/api/cron/deal-notifications`**, which **is** registered in `vercel.json` and runs daily at 00:30 UTC. Editing that function in place to serve broadcast silently changes a live daily job that notifies every subscribed user about deals.
>
> **Requirement C-21.** Phase C introduces its **own** audience builder. It does not modify `getAllSubscribedUserIds()`, and a test pins the deal cron's audience behaviour so a future refactor of one cannot quietly redefine the other.

> ⚠️ **And there are two seam-bypassing paths, not one.** `/api/cron/deal-notifications` also calls `emitNotification` per user directly under `Promise.allSettled` — no cap, no dedupe, no audit record — exactly the shape §14 describes for the legacy broadcast route. Retiring the legacy route alone would not close the pattern. **This contract does not change the deal cron**; it records that O-4's real subject is a *class* of path, and that a second decision may be needed later. That is noted, not smuggled in.

## 2. Audience

**Audience = every user with at least one enabled subscription, at the moment the send starts.**

| Question | Answer |
|---|---|
| Users with no subscription | **Excluded entirely** — no push and no inbox row (O-1 = B) |
| Users with a disabled subscription | Excluded. `enabled = false` is the person's own "no", or a transfer, or a pruned dead endpoint — all mean *do not push* |
| Anonymous sessions | **Excluded.** They are `auth.users` rows and can hold subscriptions; a broadcast is a message to members. Requirement **C-2**: the audience query excludes `is_anonymous = true`, with a test |
| Suspended / banned accounts | **Excluded entirely** — no push and no inbox row (O-2 = A). §2.2, and it is **not** a one-line filter |
| Snapshot vs live | The audience is **materialised once** at the start. A person who subscribes mid-send is not in this broadcast |

### 2.1 Push and inbox — ✅ **O-1 = B**

**No subscription ⇒ no broadcast inbox row.** The audience is the whole gate: being in it earns both deliveries, being outside it earns neither.

The measured facts this was decided against:

- `emitNotification` **always writes the `notifications` row first**, then attempts push. With no subscription: `attempted = 0` → `push_status = 'skipped'`.
- The legacy broadcast route nevertheless **iterates only subscribed users**, so a person who never enabled push receives nothing today. **B preserves that.**
- 🚨 **There is no notification preference in the product.** Nothing separates "the bell in the app" from "a push on my phone". The only signal that exists is the push subscription — which is exactly why turning it off is treated as a refusal of both.

**Requirement C-22.** The three concepts are recorded, as decided: **push opt-in** = the audience condition · **broadcast inbox row** = travels with the audience · **notification preference** = does not exist and is **not created by Phase C**. If the product later wants "inbox yes, push no", that is a new preference and a new decision — this contract does not pre-empt it, and does not leave room for it to be added by accident.

> 🚨 **`emitNotification` is not modified. Requirement C-30 (§0.1).** O-1 = B is delivered by audience construction alone. An implementation that adds a "skip the inbox row" branch to the shared emit path would change every other caller and is out of contract.

### 2.2 Suspended and banned accounts — ✅ **O-2 = A**

**Excluded entirely — no push, no inbox row.**

🚨 **This is not a one-line filter, and the schema is why.** MEASURED — `public.account_status` (`20260819_m08_account_status.sql`):

```sql
user_id UUID PRIMARY KEY REFERENCES public.profiles(id)
is_suspended BOOLEAN NOT NULL DEFAULT false,
suspended_until TIMESTAMPTZ,
is_banned BOOLEAN NOT NULL DEFAULT false, ...
```

Two traps, each of which produces a *silently wrong audience* rather than an error:

| | Trap | Wrong result |
|---|---|---|
| **1** | **Most users have no `account_status` row at all.** The row is created by an administrative action; `user_id` is a PK/FK, not a backfilled column | An `INNER JOIN` excludes **almost the entire audience**. A broadcast would appear to succeed and reach almost nobody |
| **2** | **`is_suspended` stays `true` after `suspended_until` has passed.** Auto-unsuspend is a cron, and a cron is not a guarantee | Reading the raw column excludes people whose suspension **already expired** — a lapsed 7-day suspension becomes a permanent one, invisibly |

**Requirement C-31.** The eligibility filter is a **LEFT JOIN**, and **absence of a row means eligible**.

**Requirement C-32.** Exclusion uses **effective** status, not the raw column: banned, or suspended **and** (`suspended_until IS NULL OR suspended_until > now()`). This must match `src/lib/account/accountStatus.ts`, which already computes it this way — **one definition of "suspended", not two.** If the two can drift, a test must fail.

**Requirement C-33.** Two tests, and the second is the one that matters: a **banned** and a **currently-suspended** user are excluded; **and** a user with **no status row** and a user whose **suspension has expired** are **included**. A test that only checks exclusion passes against an empty audience.

### 2.3 Subscription semantics — ✅ settled

- `enabled = false` means **do not send**, in every case — a person's own refusal, an ownership transfer, and a pruned dead endpoint are indistinguishable at send time and are treated identically.
- A user with **no row** and a user with a **disabled row** are now the **same in every respect**: outside the audience, no push, no inbox row (O-1 = B).
- Anonymous sessions hold real subscriptions and are **excluded** (C-2).
- **Audience, complete:** enabled webpush subscriptions belonging to **active, eligible, non-anonymous** accounts, materialised once, in a deterministic order (§4.1).

## 4. The cap is a design decision, not a detail

```ts
export const MAX_RECIPIENTS_PER_DISPATCH = 500
```

The seam refuses more than 500 recipients per dispatch, and it owns that cap so neither caller can exceed it.

**A broadcast to "everyone" therefore does not fit through the seam the moment the subscriber base passes 500.** Production has **one** enabled subscription today, so this would not bite for a long time — which is exactly why it must be decided now rather than discovered later.

**Open question O-3 — three ways out, and they are not equivalent:**

| Option | What it means |
|---|---|
| **A. Keep the cap, chunk the send** | Broadcast becomes N dispatches of ≤500. Needs a job, resumability, and a partial-failure story. The cap keeps protecting Marketing |
| **B. Raise the cap for broadcast only** | A second, larger cap the seam knows about. Simpler, but the number stops meaning "the most anyone can send at once" |
| **C. Broadcast bypasses the seam** | ❌ **Rejected in this draft.** It would duplicate fan-out, result aggregation and audit — the exact divergence the seam exists to prevent, and the existing `/api/notifications/broadcast` already demonstrates that failure mode by writing no audit record at all |

Recommendation: **A**, and the chunking belongs to the broadcast caller, not the seam. **A recommendation is not a decision — O-3 is still the Owner's.**

**Requirement C-23.** No path may call an internal dispatch function to get around the cap. Every dispatch, on every option, is **≤ 500**.

### 4.1 Deterministic ordering — ✅ decided by necessity, and **today's code does not satisfy it**

🚨 **MEASURED — this is a real gap, not a hypothetical.** The audience query is:

```ts
.from('notification_subscriptions').select('user_id').eq('enabled', true)
```

**There is no `ORDER BY`.** PostgreSQL is free to return those rows in any order, and it changes in practice — after an update, a vacuum, a plan change from seq-scan to index-scan. `new Set(...)` then preserves whatever arrival order it was given.

Why that is fatal to a resumable chunked send, independent of which option O-3 takes: "chunk 3 of 12 failed, resume from chunk 3" is meaningless if re-running the query yields a **different chunk 3**. Some people get the message twice, others never.

**Requirement C-24.** The broadcast audience is **totally ordered by a stable key** — `user_id` ascending is sufficient and needs no new column — and the ordering is applied **in the query**, not in JavaScript after the fact, so it survives pagination.

**Requirement C-25.** A test asserts the same audience, queried twice, yields the **same sequence** — not the same set. A set-equality assertion would pass against exactly the bug this prevents.

> This requirement holds under **A**, **B** and any option C. It is listed as decided because it is not a preference — without it, no resumable or idempotent broadcast is possible at all.

### 4.2 Chunking — ✅ **O-3 = A**

**The cap stays at 500. The broadcast chunks under it. Nothing bypasses the seam.**

| | Rule |
|---|---|
| Chunk size | **≤ 500**, every dispatch, always. The seam keeps refusing more and that refusal is never worked around |
| Ordering | the total, stable order of §4.1 — chunk *k* is the same recipients on every run |
| Boundaries | derived from the ordering, **not** from a cursor over an unordered query. Chunk *k* = rows `[k·N, (k+1)·N)` of the ordered audience |
| Where chunking lives | the **broadcast caller**, never the seam. The seam's job is to refuse >500, not to know what a campaign is |
| Audit | **one record per campaign** (C-15) plus per-chunk results (§8). Not one audit record per chunk |
| Cancellation | stops **subsequent** chunks (C-13). Already-dispatched chunks are already delivered and the report says so |

**Requirement C-23** (restated as binding): no path calls an internal dispatch function to get around the cap. Every dispatch, on every code path, is ≤ 500.

**Requirement C-34.** No recipient appears in two chunks, and no recipient is skipped between them. The audience is **partitioned**, not sampled. Test T-19 asserts the union of all chunks equals the audience **exactly** — same multiset, no duplicate, no omission.

## 5. Idempotency, retry and partial failure

**Idempotency today** is a 60-second sha256 fingerprint in the seam (`distributedRateLimit`). That is duplicate *suppression* for a double-clicked button — it is **not** an idempotency key, and it must not be described as one.

**Requirement C-7.** A broadcast carries an explicit **idempotency key**, supplied once and reused across chunk retries, so a resumed job cannot re-notify the people it already reached.

**Failure semantics, stated honestly** — the vocabulary is already fixed by the send path and must not drift:

| Term | Meaning |
|---|---|
| `accepted` | the push service accepted it. **NOT "the device displayed it"** |
| `failed` | transient error, retry-worthy |
| `gone` | 404/410 — the endpoint is permanently dead; `send.ts` prunes it by setting `enabled = false` |
| `unreachable` | the recipient had no enabled subscription |

> 🚨 **The word "delivered" is forbidden**, and there is already a test that fails on it. Neither Web Push nor FCM confirms display.

**Requirement C-8.** Partial failure is reported per chunk and in aggregate, and a broadcast that fails halfway says **which recipients were reached**, not just a count.

**Requirement C-9.** The `push_status` `gone → sent` defect is a **known, Owner-deferred** bug. This contract does not fix it and does not depend on it. If broadcast reporting would make it visible at scale, that is a reason to raise it with the Owner — not to quietly fix it inside this work.

### 5.1 Retry and idempotency under chunking — ✅ **follows from O-3 = A**

**The campaign is the unit of identity.** A campaign has an **idempotency key**, generated once when the broadcast is created and reused by every chunk, every retry and every resume of that same logical broadcast.

**Requirement C-35 — the key is per recipient, not per run.** The effective identity is `(campaign_key, user_id)`. A per-run key cannot answer the only question that matters on resume: *has this person already been notified?* Chunk indices cannot answer it either, because they are positions, not people.

**Requirement C-36 — retry preserves recipient identity and order.** A retried chunk resolves to the **same recipients in the same order** as its first attempt. It does not re-query the audience live: re-querying mid-campaign would pick up people who subscribed since the snapshot and drop people who unsubscribed, and both changes silently violate C-34.

**Requirement C-37 — the genuinely hard case, stated rather than hidden.** A chunk can fail **after** dispatch but **before** its result is recorded. On resume, that chunk's state is unknown. Under C-35 that is survivable — the per-recipient key makes a re-send a no-op — and this is precisely why the key is per recipient. Any design that cannot answer this case is not acceptable.

**Requirement C-38 — retry is bounded.** A finite attempt limit per chunk, then the campaign stops and reports. An unbounded retry against a push service that is refusing is an outage amplifier, not resilience.

**Requirement C-39 — no duplicate anywhere.** Replaying a campaign key must not create a second audit record, a second inbox row, or a second push for anyone already reached. Duplicate suppression is **not** the seam's 60-second fingerprint (§5) — that window is far shorter than a chunked campaign and must never be relied on for this.

## 6. Stale credentials

A credential can be stale in two different ways, and only one is handled today:

1. **Dead** — the push service answers 404/410. `send.ts` prunes it. ✅ handled
2. **Wrong owner** — the browser now belongs to somebody else. Closed for the *login* path by **I2** (`/api/notifications/subscribe/reconcile`), verified in production on 2026-08-30.

**Requirement C-10.** Broadcast changes neither. It must not "repair" ownership as a side effect of sending: a send path that mutates ownership is a send path that can be used to mutate ownership.

## 7. Rate limiting and abuse

**Requirement C-11.** A broadcast-specific limit, distinct from the per-actor admin limiter. The relevant unit is **broadcasts per day**, not requests per minute — the harm is one unwanted message to everyone, not a burst.

**Requirement C-11a — the unit, stated precisely, because chunking makes the naive reading wrong.**

| | |
|---|---|
| **Subject** | the **actor** (the `super_admin` or Owner who sends), **and** the platform as a whole — a second admin must not double the volume a person receives |
| **Counted unit** | **one campaign = one unit.** ⚠️ **A chunked campaign is N dispatches through the seam. Counting dispatches would rate-limit a large audience into failure while a small one passed** — the limiter would punish reach, not frequency |
| **Window** | per **day**, matching the harm |
| **Not this** | the seam's 60-second duplicate fingerprint is **not** a rate limit and never satisfies C-11 |
| **On exceed** | the campaign is **refused before the first chunk**, never mid-run. A half-sent broadcast stopped by a limiter is the worst of both outcomes |

**Requirement C-12.** **Dry run first.** The route supports a mode that resolves the audience, writes the audit record, and sends **nothing**, returning the count and the sample it would have reached. This is how the first real broadcast gets reviewed before it exists.

**Requirement C-13.** **Kill switch.** A way to stop an in-flight chunked broadcast, and a way to disable the surface entirely without a deploy.

**Requirement C-14.** **Two-step confirmation** in the UI, showing the resolved audience count from the dry run. Typing a confirmation phrase, not a second button.

## 8. Audit, logging and privacy

**Requirement C-15.** One audit record per broadcast, through `writeAuditLog`, carrying the actor, the origin (`'controller'`), the action, the audience size and the idempotency key.

**Requirement C-16.** **No recipient identity in the audit record** — the existing dispatch audit already records the actor only, and that is deliberate.

**Requirement C-17.** **No raw push endpoint or FCM token in any log, error, response body or URL.** Where a credential must be identified, use 8 hex characters of its sha256. An endpoint names one person's browser; it does not by itself allow sending a push — that needs the VAPID private key and the subscription's encryption keys — but it is the single input that can silence that device.

---

## 9. Observability

**Requirement C-18.** A broadcast reports, per run: audience size · chunks · accepted · failed · gone · unreachable · duration. Aggregate counts only.

**Requirement C-19.** `gone` counts are expected to be non-zero and are **not** a failure signal — they are the prune working.

### 11.1 Rollback and operational behaviour

**A sent broadcast has no rollback.** That is the premise of this whole document, and it is why the controls sit *before* the send: dry run (C-12), two-step confirmation (C-14), kill switch (C-13).

What **can** be rolled back, and must be, per layer:

| Layer | Rollback |
|---|---|
| Code | Ordinary revert. The feature ships **disabled**; the first deploy changes nothing observable |
| Surface | C-13's kill switch disables it **without a deploy** — the reason it is a requirement and not a nice-to-have |
| In-flight run | Cancellation stops **subsequent** chunks. Recipients already dispatched to are already reached, and the run report must say so plainly rather than reporting the run as "cancelled" |
| Inbox rows | Deleting rows already read is not a rollback, it is a second surprise. **Out of scope** — if a broadcast must be retracted, that is a product decision needing its own contract |
| Schema | Phase C introduces **no migration**. If that stops being true, the migration ships with a rollback file, per the repo's existing practice |

**Requirement C-26.** The feature is behind an off-by-default switch from the first commit, so that merging, deploying and enabling are three separate acts.

A 410 that nobody hits is cheap proof; a deletion that breaks something unknown is not recoverable by revert alone once a cron elsewhere has started failing silently.

### 14.4 How step 7's evidence is produced — and why it needed solving

🚨 **The clause "evidence, not elapsed time" was nearly unsatisfiable when it came due.** `vercel logs` returns no request records for this project and GCP logging is inert (`GCP_LOGGING_ENABLED` is unset, so it emits nothing). "We saw no calls" would therefore have meant "we cannot see calls" — an assumption wearing the costume of a measurement, which is the precise thing this clause was written to forbid.

**Owner decision, 2026-08-31: the 410 handler records its own evidence.** Every hit writes one `audit_log` row under action **`notification.broadcast.legacy_gone`**, target type `notification_broadcast_legacy`.

| Property | Design |
|---|---|
| Actor | sentinel `00000000-…-0000`, role `none`. `audit_log.actor_id` is `UUID NOT NULL` with **no** foreign key, so this needs no migration. There is no actor on a retired machine endpoint, and inventing one would put a false name in the audit trail |
| Signal recorded | **whether** an `Authorization` header was present — a boolean. A hit carrying a credential is a plausible real caller; a bare hit is most likely an internet scanner. **The header's value is never read, compared or stored** |
| Never recorded | the credential · message title or body · endpoint · email |
| Abuse bound | evidence writes are capped by a limiter on a key **separate from the broadcast limiter**, so an anonymous scanner can neither fill `audit_log` nor consume the Controller's daily campaign budget |
| Failure behaviour | the **410 never depends on the evidence path**. Limiter outage, refusal, or an audit throw all still return 410 — a retirement notice that could 500 would be worse than the route it replaced |

**Acceptance criterion for step 8:** a queried window over `audit_log` where `action = 'notification.broadcast.legacy_gone'` returns **zero rows**, and in particular zero rows with `had_authorization_header = true`. 🚨 **An empty query result is only evidence if the mechanism is known to work** — so the query must also confirm the action appears at all when deliberately exercised. "No rows" from a recorder that was never wired up is the same false negative in a new costume.

### 14.5 What actually happened — the recorder was broken, and the clause caught it

**The first attempt at step 7 was aborted, and that is the useful part of this record.**

MEASURED 2026-08-31: of four hits on the 410, the **first — on a cold serverless instance — wrote no audit row**; three on a warm instance did. `writeAuditLog` is fire-and-forget, and Vercel can freeze an instance the moment the response returns, discarding un-awaited work. A rare real caller is precisely the request most likely to arrive cold, so **the recorder was weakest exactly where the evidence had to be strongest**. Had the window run on that recorder, "0 hits" would have meant "we cannot see hits" — this clause's own failure mode, wearing the clause's own clothes.

Fixed in [#221](https://github.com/huyphamsm-tappy/tappyai-mvp/pull/221): `writeAuditLogAwaited()` holds the body and returns `Promise<boolean>`; `writeAuditLog` delegates to it with `void`, so **every other caller's behaviour is unchanged**. Only this route awaited. Proven afterwards in production on a genuine cold start — the first request to the new deployment recorded — and by two independent signatures of an awaited write: response time ~700–1200 ms instead of ~50 ms, and the row readable with **zero** query delay where a 2.5 s sleep had previously been needed.

**Then the window ran and returned 0.** The route is deleted at step 8; the action name `notification.broadcast.legacy_gone` is recorded here because the historical `audit_log` rows outlive the code that wrote them, and the constant module that held it was deleted with the route.

> 🔑 **The lesson is not "await your audit writes."** It is that an absence is only evidence when the instrument has been shown to register a presence. Everything else in this section is bookkeeping.

**Requirement C-29.** While the route survives, a test pins that it stays unused: unreachable from `vercel.json` cron and unreferenced by product code, so "unused" cannot quietly become "used again" between step 1 and step 8.

**Requirement C-40.** The 410 at step 6 must be a **behavioural** test — a request receives 410 and **writes nothing** — not a source-text assertion. This repository already has a guard that scanned source and stayed green while the behaviour was off (U02).

### 14.3 Scope, stated so the decision is not over-read

⚠️ §1.3 records a **second** seam-bypassing path: `/api/cron/deal-notifications`, which **is** live and scheduled daily. O-4 covers the legacy broadcast route **only**. Retiring it does not close the class, and **this contract changes nothing about the deal cron**. Whether that path should also be brought under the seam is a **separate, unmade decision** — recorded here so it is not mistaken for something O-4 already settled.
