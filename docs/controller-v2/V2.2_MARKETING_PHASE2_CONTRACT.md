## 2. Consent model — **REQUIRED BY EXISTING DOC** + **OWNER DECISION**

**REQUIRED** — [`33_Privacy_Data_Governance.md`](../backoffice/33_Privacy_Data_Governance.md) §5:

> *"Marketing notifications — **Opt-in per channel**; global unsubscribe honored immediately."*
> *"Essential/operational — Auth, security, and transactional events are **not opt-out**."*
> *"**Consent state is stored per user** and is included in their data export."*

**OWNER DECISION 2026-09-01:** marketing consent is **opt-in**, and **existing users default to opted-out**.

🚨 **The default is the whole decision, and it must not be softened during implementation.** Opt-in means **silence is not consent**. Every user who exists on the day this ships is opted **out** until they act. A migration that backfills existing users as opted-in would convert a legal posture into its opposite with one `UPDATE`, and would look like a reasonable default while doing it.

**PROPOSED — Requirement M-1.** Consent is stored per user, per channel, with the row's **absence meaning opted-out**. No backfill of existing users. A test asserts that a user with **no consent row** receives nothing.

### 2.1 Consent export is a **hard dependency on activation** — **OWNER DECISION**

**REQUIRED** — 33 §5: *"Consent state is stored per user and is included in their data export."*

**OWNER DECISION 2026-09-01:** that requirement is a **hard dependency for Marketing activation**. Verify first whether an existing mechanism already satisfies it; **do not invent a second export system, and do not claim compliance if no mechanism exists.**

**MEASURED 2026-09-01, re-verified 2026-09-01 on `f7efc54` — no export mechanism exists, of either kind.**

### 2.1.1 🚨 There are TWO different things called "export"

An earlier revision of this section conflated them. They are not the same mechanism and do not answer the same requirement:

| | Export | Source | What it actually is |
|---|---|---|---|
| **E1** | **Bulk / admin / reporting** | [`05_API_Architecture.md`](../backoffice/05_API_Architecture.md) §14 — body `{"type":"user_list","format":"csv","filters":{…}}` · [`23_Implementation_Roadmap.md`](../backoffice/23_Implementation_Roadmap.md) Phase 5, *"Reporting & Export"*, success criterion *"Excel export of user list works"* · [`03_Module_Architecture.md`](../backoffice/03_Module_Architecture.md) Module 19 "Export Center" (that document is **DRAFT — Awaiting Owner Approval**) | An operator exporting **many users** for reporting. `23` Phase 5 mentions GDPR **zero times** and consent **zero times**; Module 19's export types are user list, event log, audit log, analytics snapshots and reports — **portability and consent are on neither list** |
| **E2** | **Per-user portability / Subject Access Request** | [`10_User_Management.md`](../backoffice/10_User_Management.md) §5 — JSON zip, signed URL valid 1 hour, audit log entry | **One user's own data**, the GDPR access right |

🔑 **[`33_Privacy_Data_Governance.md`](../backoffice/33_Privacy_Data_Governance.md) §6 routes Access / Portability to `10` §5** — its *Owner Doc* column names `10` §5 for that right. The `33` §5 sentence this requirement rests on therefore points, on the available evidence, to **E2 rather than E1**.

**[OWNER DECISION REQUIRED]** — whether M-30 is answered by E2, by E1, or by both. This contract does **not** decide it. Note that `33` §6's column is headed *Owner Doc*: it names the **document** that owns the mechanism, not the team or workstream that delivers it, so it does not answer Q6 either.

**Neither E1 nor E2 exists.** Both are SPECIFIED ONLY: no export route anywhere in `src/`, `POST /api/admin/export` returns **404** on production, 0 tests, 0 export permission in the registry, 0 export module among the 13 registered module manifests.

### 2.1.2 What `10` §5 collects — and what cannot be concluded from it

`10` §5 lists *profile, conversations, reviews, interactions, **preferences**, `ai_usage_log`, **subscriptions***. The word "consent" does not appear.

⚠️ **That is not proof that consent is excluded, and this contract must not be read as claiming it is.** `10` §5 defines neither bolded term. What is measured:

- Within `10` itself, `subscriptions` is used for the **paid plan** (`10`:25, *"From `subscriptions` table"*, Free / Pro) and `preferences` for **country and language** (`10`:29–30); where that document means push it writes **`notification_subscriptions`** in full (`10`:209).
- The two tables that exist today carry **no consent state**: `public.subscriptions` is Stripe billing (`stripe_customer_id`, `plan`, `status`, …); `public.user_preferences` holds budget, style, dietary tags, party size and a profile cache — **0 consent, marketing or notification columns**.
- Whether `10` §5 *intends* those tables is **not stated anywhere**.

⇒ Consent is **not demonstrably included and not demonstrably excluded — UNKNOWN**. **[OWNER DECISION REQUIRED]** to canonicalize what `preferences` and `subscriptions` mean in `10` §5.

**PROPOSED — Requirement M-2.** Marketing activation **must not be enabled** until consent state is exportable per 33 §5. Satisfying this means one of:

- **(a)** the export the Owner designates (E1, E2, or both — see 2.1.1) is built and **its output demonstrably includes consent state**, which may require amending the `10 §5` collection list — an edit outside this contract's scope; or
- **(b)** consent export is delivered as part of whatever export mechanism the Owner directs — **not** as a second, Marketing-only export system.

🚨 **M-30 stays UNSATISFIED regardless of how 2.1.1 and 2.1.2 resolve**, for a reason that depends on neither: **there is no consent state to export** — 0 consent table, 0 consent column, 0 per-channel consent anywhere in `src/` or `supabase/` — **and no export mechanism**. "The export exists" would still not be sufficient evidence; the export must be **shown** to contain consent state.

**Requirement M-2a.** This document records the dependency as **UNSATISFIED**. It does not claim compliance, and no Phase 2 work may mark it satisfied without showing the exported consent state itself.

## 5. Frequency caps — **REQUIRED BY EXISTING DOC**

**REQUIRED** — [`27_User_And_Notification_Journeys.md`](../backoffice/27_User_And_Notification_Journeys.md) §4:

> | Max marketing pushes per user | **1/day, 4/week** |
> | Transactional (security, moderation) | **Exempt from cap** |
>
> *"These are enforced **server-side at dispatch time**, not left to campaign authors."*

**PROPOSED — Requirement M-6.** Enforced **per recipient at dispatch time**, not per campaign. A campaign is not a unit of harm; a person receiving four pushes in an hour is.

**PROPOSED — Requirement M-7.** A recipient over cap is **skipped and recorded as skipped**, not silently dropped and not failing the campaign. The result must distinguish *sent*, *skipped-by-cap*, *skipped-by-quiet-hours* and *skipped-by-consent* — otherwise "delivered to 40 of 100" is unreadable.

### 5.1 The window — **OWNER DECISION** *(resolved 2026-09-01, was Q1)*

**Rolling 24 hours and rolling 7 days.** Limits unchanged: **1 marketing push / rolling 24h** and **4 marketing pushes / rolling 7d**, per user.

🔑 **This is an OWNER DECISION, not a doc requirement.** `27` §4 states "1/day, 4/week" and defines no window; the choice of *rolling* is the Owner's and must not be re-labelled as REQUIRED later.

**PROPOSED — Requirement M-6a.** The window is computed **backwards from the moment of dispatch** against that recipient's marketing delivery history — not from a day boundary, not from a campaign start time. Calendar semantics would permit two sends 60 seconds apart across midnight while both "obey" 1/day; rolling closes that.

**PROPOSED — Requirement M-6b.** Both windows are enforced independently and the **stricter one wins**. A recipient who has received 4 marketing pushes in the last 7 days is skipped even if none of them fell in the last 24 hours; a recipient with 1 in the last 24 hours is skipped even if their 7-day total is 1.

**PROPOSED — Requirement M-6c.** The history read is the **delivery record** (§9), which is the only durable per-recipient evidence of a past marketing send. If a delivery is not recorded, it is invisible to the cap — so the recording is part of the cap, not an accessory to it.

## 6. Quiet hours — **REQUIRED BY EXISTING DOC**

**REQUIRED** — 27 §4: *"Quiet hours (VN time) — No marketing push 22:00–07:00."*

**PROPOSED — Requirement M-8.** Evaluated server-side in **Asia/Ho_Chi_Minh**, not in the server's local zone and not in the browser's. A quiet-hours rule that depends on where the process happens to run is not a rule.

**PROPOSED — Requirement M-9.** Boundaries are explicit and tested: 21:59 sends, 22:00 does not, 06:59 does not, 07:00 does. Off-by-one at a boundary is the whole failure mode.

### 6.1 Blocked recipients are **dropped, not deferred** — **OWNER DECISION** *(resolved 2026-09-01, was Q2)*

**DROP.** A recipient inside quiet hours is **skipped for this campaign and never sent later**. Scheduling and queueing remain explicitly out of Phase 2 (§11).

🔑 **This is what keeps §11 honest.** Deferral would have required a queue, a queue is scheduling, and scheduling is out of scope — the contract would have contradicted itself one section later. Dropping is the only resolution that leaves Phase 2 inside its own boundary.

**PROPOSED — Requirement M-9a.** The skip is **observable in the campaign result and the audit record** as a distinct reason — `skipped-by-quiet-hours`, separate from cap and consent skips (M-7).

🚨 **Requirement M-9b — observable does not mean identifiable.** The skip reason is reported as a **count**, never as a recipient list, user id, endpoint or email. "17 skipped by quiet hours" is the whole of what an operator sees. A reason code attached to identities would turn the governance log into exactly the per-user surface §8 forbids.

**PROPOSED — Requirement M-9c.** An operator sending to a wholly-quiet-hours audience gets a campaign that **completes with 0 sent**, not an error and not a silent success. A drop that reads as a failure invites a retry, and a retry at 03:00 is the harm the rule exists to prevent.

## 8. Audience model and the privacy boundary — **OWNER DECISION**

**Ad-hoc filters only. No saved segments. Individual identifiable-user targeting is FORBIDDEN.**

🚨 **Requirement M-12 — the boundary is a hard floor, not a guideline.** A filter that resolves to a single identifiable person turns a marketing tool into a surveillance-adjacent one, and the resolved-audience UI would then be a way to confirm that a *specific named person* matches a *specific behavioural predicate*.

### 8.1 The privacy floor is **10 distinct eligible users** — **OWNER DECISION** *(resolved 2026-09-01, was Q3)*

**Minimum audience: 10 distinct eligible users. Enforced server-side as a refusal, not a UI warning.**

🔑 **Labelled OWNER DECISION deliberately, and it must stay that way.** No existing document in this repository specifies a k-anonymity threshold. The number 10 is the Owner's judgement, not a derivation from `27`, `33` or `34`, and re-labelling it REQUIRED BY EXISTING DOC later would manufacture a provenance that does not exist.

**PROPOSED — Requirement M-12a.** The floor is checked **server-side, in the activation path**, and a campaign below it is **refused with the campaign not activated**. A UI-only floor stops nobody who can call the endpoint (M-22).

**PROPOSED — Requirement M-12b.** The count is of **distinct eligible users** — the audience *after* consent, unsubscribe, account-status and eligibility filtering, not the raw filter match. A filter matching 400 people of whom 3 have consented is an audience of 3, and refusing it is the entire point.

🚨 **Requirement M-12c.** The refusal must not report **how far below** the floor the audience fell. "Audience is 2, minimum is 10" is a query oracle: an operator could binary-search a predicate down to one person by reading the numbers back. The refusal states that the floor was not met, and nothing more.

**PROPOSED — Requirement M-12d.** The floor applies to the **dry run as well as the real send**. A dry run that reports an audience of 2 has already leaked what the refusal was protecting.

**EXISTING** — [`src/lib/notifications/broadcastAudience.ts`](../../src/lib/notifications/broadcastAudience.ts) is the working reference: INNER join on `profiles` for membership, LEFT join on `account_status` for eligibility (absence = active), effective suspension via the shared `evaluateAccountStatus`, and an explicit `ORDER BY` in the query. **Requirement M-13:** Marketing reuses that shape and gets its own builder — it must not modify Phase C's, exactly as Phase C did not modify the deal cron's (C-21).

**EXISTING:** anonymous eligibility inherits V2.2-1 — [#225](https://github.com/huyphamsm-tappy/tappyai-mvp/pull/225) blocks anonymous subscription creation, and the historical population was **measured zero** on 2026-09-01 ([`V2.2_PHASE_C_BROADCAST_CONTRACT.md`](V2.2_PHASE_C_BROADCAST_CONTRACT.md) §15.3). Marketing adds no new anonymous surface.

### 17.1 Campaign retention — **OWNER DECISION** *(resolved 2026-09-01, was Q4)*

**`marketing_campaigns` rows are retained 1 year, aligned with the delivery-record period.**

## 19. Privacy and security — **REQUIRED** + **PROPOSED**

**Requirement M-29.** No raw push endpoint, FCM token, `p256dh`/`auth` key, email address or credential in any log, audit row, API response or UI. Where a credential must be identified, use a short hash — the rule Phase C already follows.

**Requirement M-30.** Consent state is exportable per 33 §5. **Status: UNSATISFIED** — there is **no consent state to export** and **no export mechanism** of either kind (§2.1). Which export answers this requirement is **[OWNER DECISION REQUIRED]** (§2.1.1), and whether `10` §5's *preferences* / *subscriptions* already cover consent is **UNKNOWN** (§2.1.2) — but M-30 is unsatisfied independently of both. This is a **hard dependency on activation**, not a follow-up.

**Requirement M-31.** The minimum-audience floor of **10 distinct eligible users** (§8.1) is enforced **server-side as a refusal**, on both the dry run and the real send. A UI-only floor is not a privacy control, and a refusal that reports the shortfall is a query oracle (M-12c).

**Requirement M-31a.** Skip reasons are reported as **counts only** (M-9b). No governance mechanism — cap, quiet hours, consent or floor — may emit a recipient-identifying record.

**Requirement M-32.** I1 and I1′ are untouched. Marketing reads subscription ownership and never writes it — a send path that can mutate ownership is a send path that can be used to mutate ownership.

## 22. Definition of Done — **PROPOSED**

Phase 2 is complete when **all** of the following hold:

1. Governance (§2–§8) is implemented, enforced server-side, and **cannot be bypassed by a campaign author**.
2. A user with no consent row receives nothing.
3. Cap, quiet hours, unsubscribe and the audience floor are proven by **behavioural** tests — running the code, not reading it.
4. **Rolling windows are proven at the boundary**: a send at T+23h59m is blocked and T+24h01m is allowed; a 5th send inside a rolling 7 days is blocked. A calendar-window implementation must **fail** these.
5. **Quiet hours drop, and the drop is observable without identity**: boundary tests at 21:59 / 22:00 / 06:59 / 07:00 (Asia/Ho_Chi_Minh), a campaign that completes with 0 sent, and skip reasons reported as counts.
6. **The floor refuses at 9 and permits at 10**, server-side, on both dry run and real send, without disclosing the shortfall.
7. **Mutation testing kills every safety invariant**: remove the 24h cap · remove the 7d cap · make the window calendar instead of rolling · remove quiet hours · defer instead of drop · ignore unsubscribe · treat absent consent as opted-in · allow author-set category · lower or bypass the floor · report the shortfall · attach identity to a skip reason · activate without a dry run · drop the typed confirmation.
8. **Consent export (M-30) is satisfied and demonstrated** — the exported payload is shown to contain consent state. 🚨 Until then, **activation must not be enabled at all**.
9. `marketing.campaigns.activate` is proven independent of `notifications.send.broadcast`.
10. The seam is unmodified except by additive, non-authorizing change.
11. Retention pruning exists for deliveries **and** campaigns, is tested, and cannot orphan a delivery or audit record (M-27a).
12. EN/VI parity green.
13. No production send during development. The Phase C broadcast switch stays **OFF** and is not reused as a Marketing switch.
14. Every migration has a rollback file and verified grants, `service_role` named explicitly.

> 🔑 **Point 7 is the one that matters.** This repository has repeatedly shipped green suites that proved nothing — a source-text guard that stayed green with the behaviour switched off (U02), a pin that passed against a retired route, an audit recorder that silently dropped cold-start events. For rules that protect real people from unwanted messages, "the test passes" is not evidence; "the test fails when the rule is removed" is.
