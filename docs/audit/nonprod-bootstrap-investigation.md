## 1. Executive finding

**The repository cannot bootstrap an empty database into the schema `/api/chat` runs against.** This is not a matter of order alone:

- Applied in filename order, the chain fails at **file 3 of 81** (`20260627_user_memory.sql` alters `public.user_preferences`, created by file 73 `add_preferences.sql`) and has two further forward references (§3).
- **Four tables have no `CREATE TABLE` in any migration**: `reviews`, `profiles`, `user_memory`, `conversations`. Three of them are in the root `supabase-schema.sql` (a hand-run SQL-editor script, not a migration); `reviews` exists in **no** DDL in the repository at all (§4, §6).
- Even root schema + every migration does **not** reproduce the runtime schema: `user_memory.budget` and `user_memory.history` are read on every authenticated chat turn (`contextBuilder.ts`, `memoryService.ts:30`) and have **no DDL anywhere** (§7). Production carries them; Git does not.
- The repository states all of this itself: `20260712_prod_baseline…:5-9` ("A fresh / disaster-recovery environment therefore cannot be provisioned from the migration set"), `20260818_publication_boundary_rls.sql:21-24`, `docs/ios/05_DATABASE_CONTRACT.md:13` ("can only be reconstructed from a real `pg_dump`"), ADR-020, and `supabase/migrations/deferred/README.md` (a lexicographic-order bug was already found once: Analytics finding R1).

The only faithful source of the required schema is the production database itself (schema-only). **`OWNER INPUT REQUIRED: production schema baseline artifact`** — none exists locally (§5). A documented non-production project `tappyai-staging` (`nhncoqyadofojjrnpiia`) exists but its schema provenance is unrecorded and no credential for it is present: **`UNVERIFIED — DO NOT USE`** until the owner re-verifies it (§8).

## 5. Bootstrap-model analysis

**A. Can an empty Supabase project be initialised using ONLY `supabase/migrations/**`?** **NO.** Fails at file 3 in filename order; with any order it still lacks `reviews`, `profiles`, `user_memory`, `conversations`, `handle_new_user`, and the base `reviews` policies.

**B. Additional artefacts required:**

| Artefact | Exists in repo? | Content | Production-specific? | Safe to bootstrap non-prod? |
|---|---|---|---|---|
| `supabase-schema.sql` (root) | YES | schema only (tables, RLS, one trigger, `vector` extension); Vietnamese header: "Chạy file này trong Supabase SQL Editor" | it is the **original** bootstrap of the product; not a current snapshot | partially — gives `profiles`, `conversations`, `subscriptions`, `user_memory` (stale), `user_preferences`, `services`, `bookings`, `message_feedback`; **not** `reviews`, not `user_memory.budget/history` |

| Base `reviews` SELECT policy "Read visible reviews" | **NO** | — | prod-only | cannot |

| A schema-only production export | **NO** (no `*.dump`, no snapshot; only the two files above match `*schema*.sql` / `*baseline*.sql`) | — | — | this is the missing artefact |

**C. Does `supabase-schema.sql` contain all required objects?** **NO.** It has 8 tables (`profiles, conversations, subscriptions, user_memory, services, bookings, message_feedback, user_preferences`); `reviews` is absent; `user_memory` lacks `companions/timing/personality` (added by `add_memory_columns.sql`) **and** `budget/history` (added by nothing); it also drags in `services.embedding vector(1536)` and the `vector` extension, which no current code path uses.

**D. Is production relying on manual schema changes not in Git?** **YES** — §7.

## 6. `supabase-schema.sql` analysis

197 lines; idempotent (`IF NOT EXISTS`, `DROP POLICY IF EXISTS`); creates: extension `vector`; tables `profiles`(6 cols + `onboarded`, `stripe_customer_id`), `conversations`, `subscriptions`, `user_memory`(8 cols), `services`, `bookings`, `message_feedback`, `user_preferences`(6 cols); RLS enabled on all; owner-scoped policies; function `handle_new_user()` + trigger on `auth.users`. It is the pre-migration bootstrap that production was started from (its `user_preferences` and `subscriptions` definitions are the ones the migrations later `ALTER`), but nothing records whether production's versions of these eight tables still match it, and it is not referenced by any migration, ADR, test, or script.

## 11. Safety implications

- Every gap above is a **disaster-recovery gap for production**, not just an audit inconvenience: the repository cannot rebuild its own database. Recording that is within scope; fixing it is not.
- Because production's schema is partly unversioned, a non-prod environment built from Git alone would silently diverge from production — the baseline would then measure a different application (memory load fails on missing `budget`/`history`; place turns lose community ratings without `reviews`). Faithfulness requires the production schema export.
- The schema export must be **schema-only**; a data export would move real user memories/reviews into the audit environment, which this audit forbids.
